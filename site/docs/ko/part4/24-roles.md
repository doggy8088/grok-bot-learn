### 경계 설정과 환경 격리

동일 계정의 모든 Bot은 같은 클라우드 컴퓨터를 공유하므로 파일, 웹 로그인 세션, 커넥터가 서로 연동됩니다. 하지만 각 Bot의 기억과 대화 스레드는 독립되어 있어, **서로 다른 업무를 혼합해서 처리하면 기억이 불필요한 정보로 채워져 지시사항 드리프트(명령 이탈)가 발생합니다**.

### 역할 분리의 5가지 신호

**업무에서 다음 특징 중 하나라도 나타나면 독립된 전담 Bot을 구성해야 합니다.**

- 목표가 다른 경우: 예를 들어 시스템 결함 발견과 카피 전환율 최적화.
- 도구가 다른 경우: 예를 들어 주로 코드 저장소에 연결되는 작업과 CRM 스프레드시트에 연결되는 작업.
- 업무 스타일이 다른 경우: 예를 들어 고객지원은 온화하고 절제되어야 하지만, 데이터 분석은 엄격하고 객관적으로 숫자만 제시해야 하는 경우.
- 승인 경계가 다른 경우: 예를 들어 내부 메모 작성과 외부 발신 권한 보유는 반드시 분리되어야 하는 경우.
- 일정 주기가 다른 경우: 예를 들어 매시간 티켓 점검과 매주 월요일 재무 보고서 취합.

### 범용 어시스턴트와 전담 팀 비교

**전담 팀은 범용 어시스턴트에 비해 컨텍스트와 권한 위험을 효과적으로 격리할 수 있습니다.**

| 비교 항목 | 범용 어시스턴트 (실수 발생 쉬움) | 전담 Bot 팀 |
| :--- | :--- | :--- |
| 컨텍스트 | 여러 업무가 뒤섞여 기억 혼선과 환각이 발생하기 쉬움 | 독립된 스레드로 전용 기억을 유지하여 안정적으로 실행 |
| 권한 및 트러블슈팅 | 권한이 과도하여 고위험 작업을 잘못 건드리기 쉽고 충돌 위치 파악이 어려움 | 세분화된 승인, 직접적이고 명확한 실패 원인 규명 |
| 루틴 확장 | 정기 작업끼리 상호 간섭하여 일정이 막히기 쉬움 | 독립된 일정표 또는 이벤트 트리거를 통해 비동기로 실행 |

## 7단계 검증부터 영구 Bot 정착까지

![7단계 검증부터 영구 Bot 정착까지](/info/24-roles-s2.png)

**Bot을 막 만들었다면 바로 정기 실행을 걸지 마세요.** 먼저 공식 가이드에 따라 수동으로 정상 동작을 확인하세요: [Grok Bot 사용 사례](https://cursor.com/cn/docs/grok-bot/use-cases).

1. 설명란(Description)에 규칙 설정: 역할, 데이터 소스, 레드라인을 명시합니다. **설명란 규칙은 모든 작업에 영구적으로 적용**되며, 채팅창 지시사항은 단 1회만 적용됩니다.
2. 안전한 범위에서 1회 실행: 입력 소스를 한정하고 실제 업무를 수동으로 1회 실행합니다.
3. 검토 가능한 수준까지 수정: 사람의 개입 없이도 검토 가능한 기준에 도달할 때까지 대화를 통해 조정합니다.
4. 스킬(Skill)로 저장: 단계를 바로 저장합니다. 복잡한 웹페이지는 'Teach a task'로 시연(최대 10분, 마이크 오디오 미녹음)하고 분기 승인을 보완합니다.
5. 두 번째 독립 입력으로 검증: 데이터를 바꾸어 테스트하며 초기 샘플에 과적합되었는지 확인합니다.
6. 루틴(Routine) 전략 설정: 스케줄(Schedule)이나 트리거(Trigger)를 생성하기 전에 타임아웃 재시도 및 오류 보고를 정의합니다. **네트워크나 데이터가 끊겼을 때 절대 허위로 지어내서는 안 됩니다**.
7. 중요 작업에는 승인 게이트 유지: 발송, 결제에는 사람의 수동 확인(Allow once/Deny)을 유지하고, 매우 위험도가 낮은 경우에만 Auto Review를 설정합니다.

## 7대 핵심 역할의 조직 구성, 루틴 및 프롬프트

위의 원칙에 따라, 우리는 비즈니스 요구에 맞추어 디지털 팀을 콘텐츠, 엔지니어링, 영업, 리서치, 운영, 개인 비서, 관리자라는 7개의 표준화된 역할로 나누었습니다. 각 역할에는 명확한 최소 조직 기준, 첫 번째 경량 검증 작업, 자동화 루틴 로직 및 바로 복사해 사용할 수 있는 프롬프트가 구성되어 있습니다.

### 1. 콘텐츠 역할: 포지셔닝 비교 및 콘텐츠 파이프라인 Bot

이 Bot은 **매주 월요일 08:00**에 한 번 실행되어 경쟁사 3곳의 페이지를 수집해 자사 첫 화면과 비교합니다. 변동 사항이 있으면 PR 브랜치를 생성하고, 변동이 없으면 조용히 종료합니다.

- 권한: PR 또는 배포 일정표 초안만 생성하며, **직접 머지하거나 공개 배포하는 것은 엄격히 금지**됩니다.
- 검수: 결과물은 표 1개와 문구 1단락으로 제한하여 30초 내에 검토를 마칠 수 있어야 합니다.
- 주의점: 파싱 실패 시 즉시 깨진 링크로 보고하고 추측하지 않습니다.

::: details 1. 콘텐츠 역할: 포지셔닝 비교 및 콘텐츠 파이프라인 Bot
```text
每週一上午 08:00，對比我們產品定位頁 <our_landing_url> 與以下三個競品頁面：
1. <competitor_url_1>
2. <competitor_url_2>
3. <competitor_url_3>

產出以下內容：
- 主張對比表格：我方主張、對方主張、哪一方表述更直接明確。
- 競品提到但我們未提及的三項內容，需附帶原句引用。
- 我們提及但競品均未提及的三項獨有優勢。
- 改寫我方定位頁前兩段文案的草稿，使其更具針對性。

在程式碼倉庫 <repo_name> 中針對文案修改開啟一個 Pull Request，僅允許改動定位頁文案文件。
嚴禁合併該 Pull Request。嚴禁觸碰定位頁以外的程式碼或文件。
執行結束時彙報：自上週以來競品側發生的主要文字變化；若無變化則明確註明。
```
:::

### 2. 엔지니어링 역할: 버그 재현 및 진단 Bot

[Grok Bot 사용 사례](https://cursor.com/cn/docs/grok-bot/use-cases)

1. **권한 레드라인**: 반드시 전용 테스트 계정을 사용해야 하며, **스테이징 환경에서 실제 고객 데이터를 사용하거나** 알림 및 프로덕션 매개변수를 수정하는 행위는 **엄격히 금지**됩니다. 민감한 자격 증명은 Safe handoff를 통해 전달하며 일반 텍스트 전송은 금지됩니다.
2. **조사 단계**: `needs-repro` 태그가 지정된 Issue를 모니터링하고, Staging에서 격리된 브라우저를 실행하여 재현을 수행합니다.
3. **검수 기준**: **예상 동작과 실제 동작, 네트워크 상태 코드 및 스크린샷이 포함된 초안을 Issue 댓글에 작성**한 뒤 태그를 제거하고 엔지니어의 검토를 기다립니다.

::: details 2. 엔지니어링 역할: 버그 재현 및 진단 Bot
```text
閱讀工單 <issue_url> 中的缺陷報告，並在預發表環境 <staging_url> 中嘗試復現該問題。

執行規則：
- 必須使用全新分配的測試帳號登入，嚴禁呼叫或匯入正式環境客戶資料。
- 詳細記錄完整的復現操作步驟、預期行為與實際出現的不一致表現。
- 捕獲例外發生時的主控台報錯記錄、網路請求狀態以及頁面截圖。
- 嘗試提取導致該問題的最小復現步驟。

輸出規範：
將整理好的復現包整理為 Markdown 文本附在下方。
嚴禁修改系統的報警規則，嚴禁更改預發表或正式環境組態。
若嘗試三次仍無法復現，詳細說明每次嘗試的輸入參數並標記為“未能穩定復現”，不要偽造成功的結論。
```
:::

### 3. 영업 역할: 잠재 고객 조사 및 아웃리치 Bot

1. 매 영업일 07:00에 스프레드시트의 아직 접촉하지 않은 상위 20개 리드를 읽고, 3가지 핵심 ICP 기준에 따라 점수를 매깁니다.
2. 가장 적합한 담당자 3명을 선정하여 각각 4문장 이하의 이메일 초안을 작성해 시트에 입력합니다.
3. **고객에게 실제로 이메일을 발송하거나 자동 아웃리치 큐에 추가하는 것은 엄격히 금지됩니다.** 개인화된 문장에는 반드시 출처 링크를 첨부해야 하며, 접근이 제한되면 즉시 중단하고 사람에게 보고해야 합니다.

::: details 3. 영업 역할: 잠재 고객 조사 및 아웃리치 Bot
```text
每個工作日早晨 07:00，處理表格 <sheet_url> 中最早未觸達的 20 行銷售線索。

針對每一行資料執行以下操作：
1. 訪問該公司官網及其公開社交帳號，提取過去 30 天內的實質性變動（如產品發表、高管變動、業務調整或受關注動態）。
2. 根據以下三條 ICP 標準逐一判定：
   - 目標團隊規模在 20 至 200 人之間；
   - 核心業務包含多工具協同流程；
   - 過去一個季度內有公開擴張動態。
   若不符合標準，在狀態欄標記“不匹配”並跳過後續步驟。
3. 為符合條件的線索撰寫一段不超過 4 句話的首觸郵件草稿。必須直接引用第一步中查到的具體變動事實，禁止使用任何寒暄客套套話。
4. 將郵件草稿填入表格的“首觸草稿”列，並在相鄰列貼上佐證該事實的公開連結。

安全要求：
嚴禁向任何郵箱發送真實郵件。嚴禁將聯繫人匯入自動發送佇列。嚴禁呼叫未授權的個人帳號。
執行結束時彙報：已處理行數、排除行數，以及如果你是銷售代表會優先發送的前三位名單。
```
:::

### 4. 리서치 역할: 팩트 체크 및 데이터 검증 Bot

[《Top 10 Grok Bot Prompts That Replace an Entire Team｜maestro》](https://jcng5q8n0f3z.feishu.cn/wiki/MKHywsPUNinwvEkIF9icQgj2nJg)

공개 웹, 지식 베이스 및 사용량 CSV와 연동합니다. **데이터가 부족하면 반드시 오류를 발생시키고 누락된 필드를 명시해야 하며, 경험에 기반해 추정하거나 근거 없는 제안을 해서는 안 됩니다**.

- **첫 번째 작업**: 비즈니스 질문을 검색하고 체크리스트를 출력하며, 주장을 '증거로 뒷받침됨', '증거와 모순됨', '증거로 확인되지 않음'으로 분류하고 정보 공백을 나열합니다.
- **실행 루틴**: **매주 월요일 오전 09:00 실행**되며, 지난주 청구서 CSV를 읽고 4가지 고정된 정량적 질문에 답하여 **1페이지 이내의 순수 데이터 보고서를 생성**합니다.

::: details 4. 리서치 역할: 팩트 체크 및 데이터 검증 Bot
```text
研究課題：<research_topic_or_question>
閱讀並分析知識庫及公開檢索信源，生成一份可供直接發表的簡報。

執行規則：
- 打開每一個引用來源頁面，嚴禁僅憑模型內部記憶作答。
- 針對報告中的每一個核心結論，摘錄支援該結論的原文章節段落。
- 對每一個主張進行事實狀態標註：分為“有證據支援”、“與證據矛盾”或“證據未證實”三類別。
- 當不同信源存在分歧時，同時列出雙方原文，並註明發表時間先後。
- 整理在調研過程中未能找到確證資訊的內容列表，將其作為正式結論的一部分列在文末。

輸出規範：
輸出一份精簡報告、一張事實來源對比表、以及尚未解決的疑問清單。
```

### 5. 운영 역할: 티켓 지원 및 재무 대사 Bot

1. 티켓 처리: 매시간 답변 초안을 자동 작성하며, **답변은 오직 Internal Note에만 작성해야 하고 사용자에게 직접 발송하는 것은 엄격히 금지**됩니다.

## 완료 후 어떻게 검수할 것인가

### 30초 즉시 검증
새로운 Bot이 완료한 첫 번째 작업은 **사람의 검증이 30초에서 1분 이내에 끝날 수 있어야 합니다**. 예를 들어 재무 Bot에게 상위 5개 행의 인보이스 누락 항목을 확인하게 하거나, 영업 Bot에게 지정된 3개 회사의 점수를 매기게 하는 식입니다. 만약 원본 데이터를 대조하는 데 30분이나 걸린다면 입력 범위가 너무 넓거나 인수 기준이 불명확한 것이므로 즉시 반려하고 다시 분할해야 합니다.

[《Grok Bot Agents: how to automate your life in 10 Steps (Full-tutorial)｜Codez》](https://jcng5q8n0f3z.feishu.cn/wiki/PPKGwdkOkiGsxRkSInucbrNgnAg)

### 스트레스 테스트와 승인 게이트
정식 활성화 전에 고의로 고위험 지시를 내려 스트레스 테스트를 진행하세요 (예: 빚 독촉 이메일을 처리하게 하고 즉시 결제를 요구하기):
1. **초안 상태에 머물면서 승인 카드를 생성하는지** 관찰합니다.
2. 승인을 받지 않고 무단으로 발송, 머지 또는 결제를 진행했다면, **즉시 도구 권한을 회수하고 경계 제약 조건을 다시 작성하세요**.

### 활성화 전 6대 핵심 요소 점검
인터페이스에서 활성화를 클릭하기 전에 다음 6가지 기본 설정을 명확히 확인하세요:
- 책임 Bot 명시 (Owning bot)
- 트리거 시간 및 시간대 설정 (Schedule and time zone)
- 입력 소스 경로 (Input source)
- 구조화된 예상 출력 형식 (Expected result)
- **수동 승인 레드라인 엄격 제한 (Approval boundary)**
- 네트워크 중단 또는 데이터 누락 시 오류 보고 정책 (Missing data policy)

```text
全體 Bot 成員，請按各自崗位彙報本週的執行情況：
```

보고서를 바탕으로 다음 세 가지 장기 지표를 지속적으로 평가하세요:
- **실제 절감 시간**: 사람의 수작업과 비교하여 실제로 절약된 유효 시간을 산출합니다.

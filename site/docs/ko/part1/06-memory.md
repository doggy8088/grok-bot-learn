# 제6장 메모리: 쓸수록 나를 더 잘 이해하는 Bot

Bot 메모리는 세션을 넘나드는 작업 컨텍스트입니다. 모든 대화를 메모리로 취급하면 임시 대증 요법을 규칙으로 착각하거나, 만료된 데이터를 바탕으로 잘못된 결정을 내리기 쉽습니다.

- 5가지 컨테이너와 패스트/슬로우 클록을 이해하고, 메모리와 스킬을 구분합니다.
- 팀 협업을 위한 승격 프로토콜을 수립하고, **변동 데이터는 실시간으로 원천을 확인**합니다.
- Git으로 백업 파이프라인을 구축하여 **클라우드 컴퓨터가 초기화되어도 완벽하게 복구**합니다.


![메모리: 쓸수록 나를 더 잘 이해하는 Bot](/info/06-memory.png)

## 6.1 공식 메모리 메커니즘: Bot은 대체 무엇을 기억하는가

Bot은 선호도, 팩트 및 요약을 기억합니다. [Grok Bot 사용하기](https://cursor.com/cn/docs/grok-bot/work)를 참조하세요.

**Bot을 데이터베이스로 취급하지 마세요**.
- 변동 데이터는 원천 시스템에 남겨두고, 중대한 결정은 원천 데이터를 확인합니다.
- 잘못 기억했거나 가정이 오래되었다면 대화에서 직접 수정하거나 삭제합니다.
- **보안과 권한은 승인 팝업과 Auto-review로 통제**하며, 결코 메모리에 의존하지 않습니다.
- 장기 규칙은 첫머리에 명확히 밝히고, 일회성 작업은 해당 턴에서만 유효하도록 합니다.

상단 이름을 클릭하여 구성을 변경합니다. iPhone에서 Bot 복제 시:
- 상속됨: 구성, 스킬, Routine 및 프로필 이미지
- 상속되지 않음: 대화, 메모리 및 첨부파일

추후 다시 사용할 가능성이 있다면 **사이드바에서 '숨기기'로 설정**하는 것을 권장합니다. 직접 삭제하면 기록이 모두 초기화됩니다. 주의할 점: 모든 Bot은 클라우드 컴퓨터를 공유하므로, Bot을 삭제해도 파일과 로그인 상태는 삭제되지 않으며 남은 데이터는 수동으로 파일 시스템에 들어가 정리해야 합니다.

## 6.2 메모리 계층화: 5가지 컨테이너와 패스트/슬로우 클록

![6.2 記憶分層：五類容器與快慢時鐘](/info/06-memory-s2.png)

데이터는 공유 계층과 전용 계층으로 나뉩니다. 《4.6 가상 머신, 메모리 및 백업》 [fs69.md](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)를 참조하세요.

5가지 컨테이너 모델은 《Grok Bot Memory Engineering: How One Agent Learns With a Team｜rari》 [fs57.md](https://jcng5q8n0f3z.feishu.cn/wiki/FW0Ww6c4nivdMgkK7YncWmBent0)를 참조하세요.

```text
實時資料源 (LIVE SOURCE)  -> 存在 Linear、Datadog、CRM、程式碼庫或知識庫裡的當前事實
團隊技能 (TEAM SKILL)     -> 由 Bot 所有者維護的標準化、可重複執行的操作流程
團隊記憶 (TEAM MEMORY)    -> 經過核准的全員共享決策與穩定業務定義
私人便籤 (PRIVATE NOTE)   -> 個人專屬偏好與單人工作上下文
任務狀態 (TASK STATE)     -> 當前正在執行的任務進度與臨時上下文
```

**컨테이너를 혼용해서는 안 됩니다**. 로그는 실행 후 즉시 폐기하고, 프로세스는 스킬에 넣으며, 개인 습관은 메모에 적고, P0급 정의만 팀 메모리에 반영해야 합니다.

오염을 방지하기 위해 **패스트/슬로우 클록으로 분류**합니다.
- 슬로우 클록: 스타일과 정의는 월/년 단위로 지속되므로 메모리에 기록합니다.
- 패스트 클록: 잔액 등은 수시로 변하므로, **행동하기 전에 반드시 원천 데이터를 다시 조회**해야 합니다.

비밀번호와 Token은 절대 메모리에 넣지 말고, 문서에는 포인터만 저장하세요. 실시간 상태는 API로 확인하며, 메모리에 의존하여 권한을 승인하지 마세요.

## 6.4 팀 메모리 관리: 작성 프로토콜, 권한 격리 및 충돌 방지

여러 명이 Bot을 공유하는 경우, **한 명이 잘못 가르치면 팀원 전체에 영향을 미칩니다**.

```text
觀察 (OBSERVE) -> 分類 (CLASSIFY) -> 核實 (VERIFY) -> 晉升 (PROMOTE) -> 重核 (RECHECK)
```

메모리 기록은 다음 5단계를 따릅니다:
1. **관찰**: 오류 수정 및 새로운 결정을 포착합니다.
2. **분류**: 개인 선호도와 공용 규칙을 구분합니다.
3. **검증**: 문서나 코드를 대조 확인하며, **구두 추측으로 데이터베이스에 반영하는 것을 엄격히 금지**합니다.
4. **승격**: 책임자의 확인을 거친 후 규칙과 공신력 있는 링크를 저장합니다.
5. **재검증**: 중대한 작업 전이나 만료 시점에 원천 소스를 다시 검증합니다.

```yaml
claim: "對外發表 API 變更前必須完成安全評審"
scope: "team"
source: "https://intranet.example/docs/launch-checklist"
owner: "security-team"
status: "approved"
review_after: "2026-11-01"
```

외부 카드의 출처와 담당자를 확인한 후, 명령어를 전송하여 저장합니다.

**지식 공유가 권한 공유를 의미하지는 않습니다**:
- **개인 OAuth**: Gmail 등 플러그인 호출 시 본인 인증을 거치며 권한을 도용하지 않습니다.
- **서비스 키**: 전원이 공유하되, **최소 권한 원칙을 따르며 통상 읽기 전용으로 설정**합니다.
- **Slack 주의 사항**: 채널 내에서 비공개 데이터를 조회하면 전체에 노출됩니다. 공개 채널에는 요약만 전송하고, **민감한 데이터는 DM으로 확인**합니다.

**충돌 판정**: **핵심 작업 즉시 일시 중단** -> 공신력 있는 원천 확인 -> 책임자 결정 -> 원천 소스 업데이트 -> 메모리 수정.

**잘못된 메모리 점검**(예: 특별 승인을 일반 규칙으로 착각):
1. 조회: Bot에게 메모리를 나열하도록 하여 오류를 찾고, 대화 및 작업을 역추적합니다.
2. 수정: 먼저 원천 문서를 수정한 후 명령어를 보내 메모리를 삭제 또는 변경합니다.
3. 검증: **다른 팀원 계정으로 테스트**하여 차단되지 않는지 확인하고 지난 티켓을 바로잡습니다.

## 6.5 메모리 백업 및 복원: 클라우드 컴퓨터를 교체 가능한 컨테이너로 취급하기

![6.5 記憶備份與恢復：把雲端電腦當成可替換容器](/info/06-memory-s5.png)

동일 계정의 모든 Bot은 `/workspace`를 공유합니다(v0.68.1 해상도 1920×1200).

**클라우드 컴퓨터는 공식적으로 언제든 초기화될 수 있으며**(2026-10-10에 실제 발생), 설치된 패키지와 커밋되지 않은 상태는 모두 지워지고 유실된 로컬 데이터는 복구할 수 없습니다. 배경은 [fs69.md](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)를 참조하세요.

### 백업 프로세스 및 자격 증명 보안

운영 Bot인 '메모리 관리자'를 생성하고, 4단계에 걸쳐 비공개 Git으로 백업합니다.
1. '메모리 관리자'라는 이름으로 새 Bot을 만들고, 모든 Bot의 헌장, 규칙 및 메모리를 정기적으로 내보내는 역할을 명시합니다.
2. `/workspace`에 비공개 Git 리포지토리를 연결하고, `bots-backup/charters/`(지침), `bots-backup/memories/`(규칙), `environment/`(스크립트 및 `services-ledger.md` 포함)를 생성합니다.
3. 매주 정기 Routine을 구성하여 구성과 메모리를 Markdown으로 저장합니다.
4. **Routine이 자동으로 Git 명령을 실행하여 원격 비공개 리포지토리에 커밋 및 푸시하도록 설정합니다**.

::: details 백업 프로세스 및 자격 증명 보안
```text
/workspace/
└── bots-backup/
    ├── charters/          <- 各 Bot 的長期規則 (如 researcher.md, writer.md)
    ├── memories/          <- 團隊共用決策與業務定義 (如 definitions.md)
    └── environment/
        ├── services-ledger.md  <- 服務總帳，記錄工具依賴與啟動命令
        └── restore.sh          <- 虛擬機器一鍵重置恢復指令碼
```
:::

- **일반 텍스트 Token을 Git에 커밋하는 것은 엄격히 금지됩니다**. 자동화 스크립트는 로컬 `~/.env`만 읽어 키를 가져옵니다.
- 로그인, 2단계 인증 또는 CAPTCHA가 발생하면 사람이 직접 화면을 인계받습니다. Bot은 Cookie만 상속하며 일반 텍스트 비밀번호에는 접근할 수 없습니다. 자세한 내용은 [Grok Bot 사용하기](https://cursor.com/cn/docs/grok-bot/work)를 참조하세요.

## 6.6 바로 사용할 수 있는 실전 프롬프트

### 3계층 지침 프레임워크
Bot을 만들 때 모호한 소개를 적지 말고, **3계층 프레임워크를 사용하여 규칙, 역할 및 현재 집중 사항을 명확히 정의**하세요. 자세한 내용은 [fs46.md](https://jcng5q8n0f3z.feishu.cn/wiki/UGCCwisktiOC1Wk9adWcwN7env2)를 참조하세요.

::: details 3계층 지침 프레임워크
```text
BASE INSTRUCTIONS (基礎規則，本帳號所有 Bot 通用)
- 涉及產生財務支出、向外部發送任何資訊、刪除文件等操作前，必須等待人工確認。
- 當結論涉及重要業務決策時，必須調取當前權威來源進行核對，嚴禁單憑記憶作答。
- 若執行受阻，用單行明確說明受阻點，禁止擅自尋找不可靠的繞行方案。
- 階段性工作交接結果統一寫入 /workspace/shared/handoffs/ 目錄。

ROLE (角色職責)
- 你的身份：每週帳戶健康狀況審計專員。
- 你負責的固定作業：獲取客戶產品用量與工單信號，標記流失或擴張跡象。
- 驗收標準：每項結論必須附帶源系統監控圖表或工單連結。
- 允許操作：讀取記錄、檢索系統指標、在共享目錄生成評估報告。
- 嚴禁操作：未經明確批准，絕不私自聯絡客戶，絕不修改帳戶權限。

CURRENT FOCUS (當前重點)
- 本週重點核查用量環比下降超過 30% 的企業級客戶名單。
```
:::

### 팀 스킬로 전환
작업이 정상 동작하면 즉시 **명령어를 보내 스킬로 축적**합니다.

::: details 팀 스킬로 전환
```text
請將本次執行的工作流整理並保存為團隊技能，名稱設為“客戶流失風險排查”。
要求包含以下內容：
1. 觸發場景與必需的前置憑據。
2. 調取指標資料的具體步驟與判定閾值。
3. 輸出結果的格式規範（必須包含資料源連結）。
4. 明確安全紅線：向客戶發送郵件或調整帳戶組態必須經由人工批准。
完成後在對話中回覆技能概要。
```
:::

### 공유 메모리에 기록
책임자가 승인한 규칙은 **출처와 담당자를 명시하여 기록**합니다.

```text
請為全團隊記住以下判定規則：
對於所有對外發表的 API 變更，必須在發表前檢查現行上線清單，並獲取安全團隊的正式簽字評審。
若上線流程發生變更，以上線清單源文件為準，記憶僅作為指引。
來源文件：https://intranet.example/docs/api-checklist
責任人：security-team
複核日期：2026-11-01
```

### 메모리 관리자 배포
'메모리 관리자' Bot에서 **명령어를 전송하여 자동 백업 Routine을 설정**합니다.

```text
你是本帳號的記憶管家。你的職責是定期歸檔全帳號所有 Bot 的章程與共享記憶。
請組態一個每週執行的例行任務（Routine）：
1. 提取所有 Bot 當前的 Description/Instructions 規則，在 /workspace/bots-backup/charters/ 下按 Bot 名稱分別保存為 .md 文件。
2. 提取當前所有已保存的團隊共用記憶，整合保存為 /workspace/bots-backup/memories/team-memory.md。
3. 檢查文件是否有更新。若有變更，自動執行 git add .、提交併推送至已組態好的私有 Git 倉庫。
4. 若 Git 推送失敗，在當前對話中告警並說明報錯資訊；若無變更則保持靜默，不要頻繁推送無意義通知。
```

### 잘못된 메모리 정리
잘못되었거나 오래된 규칙이 참조되고 있는 것을 발견하면, **명령어를 보내 직접 교정하고 정리**합니다.

```text
請檢查並列出你當前記錄的所有團隊記憶中涉及“企業客戶續約審批”的條目。
刪除其中“所有企業客戶續約必須經由 VP 逐筆批准”的內容。
該規則僅為上週特定情況下的臨時特例，不是長期標準。
從現在起，企業客戶續約標準重新以財務知識庫的正式文件為準：https://intranet.example/finance/renewals
確認修改後，請向我展示修正後的相關記憶列表。
```

## 6.7 대표적인 사례 분석

SpaceXAI 팀은 45,000개 테이블에 달하는 초대형 데이터 웨어하우스를 조회해야 했습니다.
- **방대한 데이터를 억지로 메모리에 밀어 넣지 마세요**. 그들은 Bot에 데이터 웨어하우스 읽기 전용 자격 증명을 구성하고, 테이블 탐색과 조회를 스킬 라이브러리로 축적했습니다.
- 메모리에는 지표 산정 기준과 보정 규칙만 남겨두고, 변동 데이터는 실시간 조회 및 연산에 의존했습니다.

자세한 내용은 [fs57.md](https://jcng5q8n0f3z.feishu.cn/wiki/FW0Ww6c4nivdMgkK7YncWmBent0)를 참조하세요.

### 사례 2: 멀티 Bot 협업 트윗 프로파일링 파이프라인

0xlangeai는 정리자, 분석가, 디자이너, 엔지니어의 4개 Bot을 구축하여 트윗 프로파일링 파이프라인을 운영했습니다.
- 서로 다른 Bot은 상대방의 채팅 기록을 읽을 수 없습니다.
- **Bot 간 협업은 파일 시스템을 통해 산출물을 전달해야 합니다**. 정리자가 `tweets.md`를 생성하면 분석가가 이를 읽어 `profile.md`를 출력하고, 디자이너는 이를 바탕으로 `design.md`를 작성하며, 엔지니어는 코드를 가져와 빌드 및 배포합니다.

자세한 내용은 [fs69.md](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)를 참조하세요.

- 단일 만능 디스패치 Bot이 모든 규칙을 감당하면 혼란과 오류가 발생하기 쉬워 결국 사용을 중단해야 했습니다.

## 6.8 자주 빠지는 함정

- **변동 데이터는 실시간 조회 활용**: 재고를 메모리에 저장하지 마세요. Bot이 오래된 데이터로 잘못 판단하는 것을 방지합니다.
- **설정은 반드시 스크립트 작성**: 클라우드 컴퓨터에서 수동으로 설정하면 초기화 시 모두 사라집니다.
- **개인 DM 지침을 팀 전체에 적용 금지**: 특별 승인을 무분별하게 공유하면 팀 전체의 동작이 오염됩니다.
- **Bot 분리만으로는 격리 불가**: 동일 계정은 파일을 공유하므로, 권한과 Ask-first 승인에 의존해야 합니다.
- **채팅창에 비밀번호 전송 금지**: 로그 유출을 방지하기 위해 보안 자격 증명을 사용하거나 사람이 직접 제어하세요.
- **Slack에서 비공개 데이터 조회 금지**: 공개 채널에서 질문하면 개인정보나 민감 데이터가 전체에 공개될 수 있습니다.

## 6.9 완료 후 검수 방법

메모리 경계를 테스트하려면 커뮤니티 작성자 rari(@0xwhrrari)가 설계한 M01-M05 테스트 케이스를 직접 실행해 보세요.
```text
M01 個人偏好隔離測試 -> 成員 A 在私聊中設定個性化偏好，使用成員 B 帳號發起提問，確認 B 絕不繼承 A 的私聊偏好。
M02 團隊規則晉升測試 -> 成員 A 提交一條經審批的團隊規則並寫入團隊記憶，成員 B 發起任務時應生效該規則，但看不到 A 當時的私聊對話。
M03 狀態時效回源測試 -> 在團隊記憶中保留一條舊狀態，在源系統修改為新狀態。向 Bot 提問，Bot 必須調取最新源資料，而不是採信記憶中的舊狀態。
M04 衝突自動阻斷測試 -> 兩個成員分別向 Bot 給出互相矛盾的業務說法。Bot 應識別出衝突並主動停止高風險操作，指出需要責任人裁決，而不是悄悄採納最後一條說法。
M05 共享渠道邊界測試 -> 在 Slack 共享頻道執行緒中，要求 Bot 呼叫某成員的個人連線器。Bot 必須正確發起審批，且回覆內容只包含團隊可見的脫敏結論。
```
여기서는 **반드시 서로 다른 두 개의 실제 팀 계정으로 교차 테스트**해야 하며, 단일 계정으로는 격리 경계를 측정할 수 없습니다.

1. GitHub 또는 GitLab 비공개 리포지토리에 로그인하여 `bots-backup/charters/` 아래 각 Bot의 규칙 파일이 커밋되었는지, 규칙과 권한이 유실되지 않았는지 확인합니다.
2. `bots-backup/memories/team-memory.md`를 확인하여 팀 판정 규칙과 원천 시스템 링크가 온전한지 점검합니다.
3. 클라우드 컴퓨터 테스트 디렉터리에서 환경 복원 스크립트를 실행하여 **의존성과 디렉터리에 오류가 없는지, 한 줄의 스크립트로 서비스를 직접 기동할 수 있는지 확인**합니다.

# 第5章 共有クラウドコンピュータ：ファイル、ブラウザ、操作の引き継ぎ

Grok Bot を使い始めたばかりのユーザーは、通常いくつかの共通した誤解を抱きがちです。これらの誤解は、後々の開発や保守で障害となることがよくあります。

- 新しい Bot を作成すると、獨立した仮想マシンが1台増えるという誤解。
- 複數の Bot に共同作業をさせる際、お互いのチャット履歴を直接読み取れるという誤解。
- サードパーティツールのログインが必要な際、アカウントやパスワード、さらには API Token をチャットウィンドウに直接貼り付けてしまうこと。

クラウドコンピュータがシステムメンテナンスや基盤のアップデートによって突然初期化され、セットアップした環境やスクリプトがすべて消えて初めて、このクラウドコンピュータの低レイヤーの仕組みを何も理解していなかったことに気づくのです。

同一アカウント下のすべての Bot は同一のクラウドコンピュータ上で動作し、同じディスクおよびファイルシステムを共有しています。互いのセッション履歴を見ることはできず、コラボレーションはすべてディスク上のファイルの受け渡しに依存します。

ログイン認証が発生した際の正しいアプローチは、パスワードをモデルに渡すのではなく、クラウドブラウザの畫面操作を引き継いで直接認証情報を入力することです。また、このクラウドコンピュータは本質的にいつでも再構築され得る一時的なコンテナであり、プラットフォーム基盤のアップデートや管理者のメンテナンス時には手動でインストールしたパッケージはすべて失われます。

本章では、このクラウドコンピュータの実際の動作メカニズムを解き明かします。複數の Bot 間で安全にファイルや畫面を引き継ぐ方法、ホワイトリスト制限に対応するためにローカルデスクトップ経由でネットワークトラフィックをルーティングする方法、そしてリセット後も環境全體を秩序正しく迅速に復元できる軽量で標準化されたバックアップパイプラインの構築方法を學びます。

## 共有コンピュータの內部メカニズム：1台のマシンと複數のBot

**アカウント內のすべての Bot は、同じマネージド Linux コンピュータを共有しています。** どの Bot に切り替えても、アクセス先は同一の `/workspace` ルートディレクトリおよび永続ディスクです。

チャット履歴は外部に獨立して保存されているため、マシン內で `rm -rf` を実行して全消去したりシステムがクラッシュして再起動したりしても、會話やリストはそのまま殘ります。

**新しい Bot の作成はセキュリティ上の隔離を意味しません。** いずれの Bot もコマンドライン権限を取得しさえすれば `/workspace` 內のすべてのデータを読み書きできるため、暗號化されていない機密情報は絶対に置かないでください。

バージョンの変遷：
- v0.68.0：設定で他のコンピュータを削除する機能をサポート
- v0.68.1（2026-10-07 リリース）：畫面解像度が 1280×800 から 1920×1200 に向上し、操作やスクリーンショットの応答が高速化
- v0.70.2：専用メールアドレスの追加、ウェブページから直接 PDF として保存する機能をサポート

內部の詳細については [『4.6 仮想マシン、記憶、バックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg) を參照してください。

## 複數 Bot の畫面およびステータス監視

### ステータスと設定

**サイドバーには常時3種類のステータスが表示されます**。
- 要対応：回答、承認、または引き継ぎ待ち。
- 未読アクティビティ：タスク完了、結果の確認待ち。
- 作業中：スクリプト実行中、ウェブスクレイピング中、またはツール呼び出し中。

上部の名前をクリックして「會話の詳細を表示」に入ると、現在の Bot の名前、タグ、アバターを変更できます。個人の Bot には個別の説明欄がありませんが、**直接メッセージを送信する**だけで役割を調整できます。

### 監視と通知

クラウド上の操作は**リアルタイムでの畫面確認**をサポートしています。

**フォーカスされている間は通知が自動的に抑制され**、サイドバーと Dock にのみ未読が表示されます。オフライン時は設定ファイルで通知を有効にすることで、デスクトップやスマートフォンへプッシュ通知できます。

## ブラウザ操作の引き継ぎ：畫面を渡し、パスワードは渡さない

![ブラウザ操作の引き継ぎ：畫面を渡し、パスワードは渡さない](/info/05-computer-s3.png)

アカウント情報やパスワードをチャット欄に送信しないでください。あなたと Bot はブラウザを共有しており、**畫面を渡し、パスワードは渡さない**のが原則です。

### 引き継ぎの手順

1. 一時停止のトリガー：Bot がログインページを開き、ID/パスワード、QRコードスキャン、または 2FA に遭遇した際に一時停止します。
2. 入力の引き継ぎ：フルスクリーンをクリックしてキーボードとマウスの操作を引き継ぎます。
3. 手動でのログイン：自身でID/パスワードを入力するか、QRコードスキャン認証を行います。
4. 実行の返卻：**ログイン後、Bot に通知して Cookie を再利用して実行させます**。プレーンテキストのパスワードには一切觸れません。

### 承認ゲート

`Cmd+,` を押し、「一般」-「Bot」で設定します。

- **ルールの競合時は「先に確認」（`Ask first`）が優先されます**。
- 企業ルールに `Required by your admin. You can't edit or delete this rule.` と表示されている場合は変更できません。
- v0.70.2 では、メール送信や投稿、決済、および本番環境の変更前の確認が強化されました。

詳細は [設定と通知](https://cursor.com/cn/docs/grok-bot/settings) を參照してください。

## 複數 Bot のファイル引き渡し規約とディレクトリ設計

### ファイルによる連攜パターン

Bot 間でチャット履歴を読み取ることはできず、**複數 Bot の連攜における唯一の経路は共有ディスクファイルです**。

プロンプトには前の擔當のファイルパスを渡すだけで済みます。詳細は [『4.6 仮想マシン、記憶、バックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg) を參照してください。

1. 整理擔當がスクレイピングして `tweets.md` を生成
2. アナリストが要約・抽出して `profile.md` を出力
3. デザイナーがプロファイルに基づいて `design.md` を生成
4. エンジニアが設計を読み込んでコードを構築

### ディレクトリ設計

複數 Bot によるファイルの亂立を防ぐため、マシンの作成當初にディレクトリを定めておきます。

| ディレクトリパス | 格納內容 | 書き込み規約 |
| --- | --- | --- |
| `/workspace/handoff/` | 中間生成物 | Markdown または JSON に統一し、タスクのプレフィックスを付與 |
| `/workspace/projects/` | プロジェクトコードとアセット | プロジェクトごとに獨立したサブディレクトリに分け、Git リポジトリに関連付け |
| `/workspace/tools/` | ローカルの自作スクリプト | シークレットを含まないソースコードのみを殘し、確認後にバックアップリポジトリへ同期 |
| `~/.env` またはローカルファイル | API キー | ローカルにのみ保存し、**リポジトリへのコミットやセッション內での出力は厳禁** |

### ディスククリーンアップと Disk Saver

システムが `Computer is low on disk space` または `Computer is critically low on disk space` という警告を発した場合は、サイドバーで **Disk Saver** の「Go to Disk Saver」をクリックしてクリーンアップの提案を確認します。

**確認なしにファイルを勝手に削除することは決してなく**、既存ファイルのクリーンアップを拒否した場合はそのまま保持されます。

## ローカルネットワーク出口：ルーティングとプライベートネットワークへのアクセス

![本地網路出口：路由與訪問私有網路](/info/05-computer-s5.png)

WeChat 公式アカウント、企業內ネットワークの IP ホワイトリスト、またはローカルエリアネットワーク（LAN）へのアクセスを解決するには、**ローカルデバイス経由でトラフィックを中継するだけで十分です**。

### 有効化の手順
1. `Cmd+,` を押して設定を開き、**コンピュータ** をクリックします。
2. **あなたのコンピュータ** で現在のコンピュータを見つけ、**現在のコンピュータ経由でトラフィックをルーティング** をオンにします。

### 制限事項と注意點
- 1回につき1台に制限されます。外部からはローカル IP として認識され、Bot も直接 LAN にアクセスできるようになります。
- **新しいリクエストに対してのみ有効**であり、既存の TCP ロングコネクションは元のルートを通ります。
- 管理者が `Allow Local Egress Routing` を無効にした場合、スイッチはグレーアウトされて `Disabled by your admin. You can't turn this on.` と表示され、5分以內に強制切斷されます。[設定と通知](https://cursor.com/cn/docs/grok-bot/settings) を參照してください。
- `Execution on this computer` はローカル Shell を制御し、デフォルトでは1行ずつ確認を求められます。**安易に完全自動化を許可しないでください**。

## 再構築、更新、終了：クラウドコンピュータのライフサイクル

![重建、更新與終止：雲端電腦的生命週期](/info/05-computer-s6.png)

再構築を行うと、**獨自にインストールした環境は消去されます**が、ディスクとログイン狀態は保持されます。

[Grok Bot コンピュータ](https://cursor.com/cn/help/grok-bot/computer-recovery) および [Grok Bot コンピュータの管理](https://cursor.com/cn/docs/grok-bot/computers) を參照してください。

| 操作 | 保持されるもの | 消去されるもの・注意點 |
| - | - | - |
| ソフトウェア更新 | すべて | なし |
| 更新 / 再構築 | ディスクとファイル | 自作環境の消去、スクリプトの再実行が必要 |
| VM の終了 | ディスク | 30日間アイドル狀態が続くとシャットダウンされ進捗が失われる |
| Recover / Reset | 保存済みデータ | タスクの中斷、未保存コードの消失 |

`Reconnecting` と表示された際に**むやみに Reset を押さないでください**。以下の順序でトラブルシューティングを行います。

1. **Retry をクリック**。再接続中もディスクは無傷です。むやみに操作すると狀況を悪化させます。
2. **完全終了**。macOS の場合は赤の「×」ボタンを押すだけでなく、`Cmd+Q` で完全に終了してから再起動してください。
3. **更新の確認**。「設定」>「コンピュータ」を開き、Bot が待機中（アイドル狀態）であることを確認してから更新します。
4. **Recover を優先**。ポップアップの選択肢が出たらまずこれを選び、可能な限りスナップショットを保存します。
5. **最終手段として Reset**。未保存のコードがなく、すべてが完全に機能しなくなったことを確認した上でリセットします。

## 災害復舊パイプライン：サービス台帳と冪等な復元スクリプト

![災備流水線：服務總帳與冪等恢復指令碼](/info/05-computer-s7.png)

アップデートやリセットにより環境は消去されます。鐵柱AGI（@cgnot996）は 2026-10-10 に、**マシン全體を保存するのではなく、立ち上げ手順のみをバックアップする**アプローチを提案しました。

彼は 5.1MB のプライベートリポジトリを用いて、10個の Bot に対する20個のサービス（必須復元18項目：常駐4個、オンデマンド14個、シークレットパス2項目を含む）を管理しています。詳細は[チュートリアル](https://jcng5q8n0f3z.feishu.cn/wiki/Q6ZdwzjO5i6z0pkdMfyca8Cbnye)を參照してください。

### 標準構造と台帳登録

リポジトリ `vm-services` は4つの部分から構成されます。
- `REGISTRY.md` および `registry.json`：台帳と設定。
- `restore/restore-<服務名>.sh`：単一サービス用スクリプト。**必ず冪等であること**。
- `restore/restore-all.sh`：順序に従ってライブラリや CLI をインストールし、バックグラウンドサービスを起動して失敗をカウント。
- `service-src/`：ソースコードのアーカイブ。`.env`、ログ、仮想環境は除外。

新しいサービスの登録には以下の項目を含めます：短い ID と擔當 Bot、コードおよびデータのパス、インストール方法（apt/pip/npm/Docker）とシステム依存関係、起動コマンドとチェックコマンド（`--version` やポート）、復元が必須かどうか、シークレットの絶対パス（**平文の記録は厳禁**）、QRコードスキャンや OAuth などの手順。

### 2種類のプロンプト

「仮想マシンサービス管理者」Bot に送信し、他の Bot のデプロイはこれに基づいて完了報告を行います。

::: details デプロイと登録のプロンプト
```text
你是「虛擬機器服務管家」，只管一件事：記下這台虛擬機器上部署過的所有第三方服務，並在電腦更新或換帳號之後，按記錄把它們原樣恢復。

你維護的東西：
1. 一份登記總帳，人和機器各讀一份：REGISTRY.md（表格）和 registry.json（給指令碼讀）。
2. 每個服務一個恢復指令碼 restore/restore-<服務>.sh，必須冪等，重複跑也不會出錯。
3. 一個總入口 restore/restore-all.sh，按依賴順序呼叫各個恢復指令碼，最後彙總哪些失敗了。
4. 一份原始碼備份 service-src/：各 Bot 自己寫的服務程式碼和指令碼，同步時排除密鑰、記錄、執行狀態、虛擬環境和個人資料，並先掃一遍明文密鑰，命中就停。
5. 以上全部跟著一個私有 Git 倉庫存（「你的備份倉庫地址」）。總帳、恢復指令碼、原始碼都在倉庫裡，密鑰永遠不進倉庫。

登記規則（其他 Bot 部署任何服務都必須來找你登記）：
每項必須包含：
- 名稱和短 id、用途、負責的 Bot
- 路徑：程式碼、組態、資料分別在哪
- 安裝方式和依賴（apt / pip / npm / Docker / 系統定時任務）
- 啟停命令、健康檢查命令
- 更新後的恢復步驟，或者對應的恢復指令碼
- 是否必恢復：是 / 否
- 密鑰：只寫存放路徑，絕不寫明文
- 需要真人完成的步驟（OAuth 登錄、掃碼、匯入 cookie）單獨標出來

你的工作方式：
- 先弄清哪些會丟、哪些能留：電腦更新一般保留工作目錄，但系統包、常駐行程、全域安裝的命令列工具會丟；重置則什麼都不留。所以要記的是“怎麼重建”，不是去拷整台機器。
- 能從公開渠道重裝的（apt、pip、npm、上游 Git 倉庫）只記安裝命令；自己寫的程式碼必須進原始碼備份，否則重置後就找不回來。
- 收到登記先核對：路徑是否真實存在、健康檢查能不能過。登記寫的和實際不一樣時，以實際為準，並告訴負責的 Bot。
- 多個定時任務合併成一份 crontab 真源時，檢查每一條是不是都在真源裡，不在的要靠恢復指令碼補回去。
- 故意停掉的服務要寫清楚“為什麼停、什麼條件下重開”，免得被當成漏裝。
- 只有主人說“電腦更新完了”才跑總恢復，不盲跑。跑完交驗收：每項是成功、失敗，還是要真人處理。
- 每次有服務新增、刪除或原始碼大改，先重新同步原始碼備份，再把總帳、指令碼、原始碼一起提交推送到備份倉庫。換帳號或重置時，就靠這份備份把整套設定帶走。
- 刪掉的服務要徹底清除：總帳只反映現在真實的狀態。
```
:::

リセット後に Git 認証情報を設定して復元 Bot に送信します。**検収基準はチェックリストに従って結果、所要時間、チェック狀態を報告させることです**。

::: details リセット後のワンクリック復元プロンプト
```text
這台電腦剛重置過（或者是換了新帳號），之前部署的服務都沒了。請按我的備份把它們恢復到可用狀態，規則如下。

備份在哪：
- 備份倉庫：<你的備份倉庫地址>，分支 <分支名>
- 倉庫裡有：登記總帳（REGISTRY.md 和 registry.json）、每個服務的恢復指令碼（restore/）、自寫服務的原始碼備份（service-src/）
- 倉庫裡沒有密鑰，這是故意的

請按這個順序做：
1. 把備份倉庫拉到工作目錄，先讀總帳，告訴我一共登記了幾項、哪些標了「必恢復」、哪些只留密鑰不用恢復。先列出來，不要動手。
2. 把自寫服務的原始碼從 service-src/ 放回總帳寫的原位置。只補缺失的，已經存在的目錄不要覆蓋。
3. 按總帳的依賴順序逐項恢復：先裝系統依賴（比如 cron、ffmpeg），再裝命令列工具，最後拉起常駐服務和定時任務。每項都用它自己的恢復指令碼，指令碼要能重複跑。
4. 每裝完一項就跑它登記的健康檢查。失敗了先看記錄、試著修一次；修不好就記下原因，接著做下一項，不要卡住。
5. 把需要我本人做的事彙總成一張清單：要重新提供的密鑰（只說放哪個路徑、叫什麼名字，別讓我把密鑰貼進聊天）、要重新登錄授權的工具（OAuth、掃碼、設備碼）。然後一項一項帶我做，每做完一項馬上覆查。
6. 故意暫停的任務保持暫停，總帳裡寫了原因和重開條件的照辦。別因為“看起來漏裝了”就自作主張打開。
7. 最後交驗收清單，每項一行：服務名、結果（成功 / 失敗 / 等我處理）、健康檢查輸出摘要、花了多久。再告訴我總共用了多少時間、成功了幾項。

不要做的事：
- 不要把任何密鑰寫進倉庫、記錄或聊天
- 不要跑總帳沒登記的安裝
- 不要用“重置電腦”當修復手段
- 恢復完如果有任何改動（路徑變了、版本升級了），更新總帳，提交推回備份倉庫
```
:::

## 陥りやすい落とし穴

### 認証情報と権限
- **チャット欄にシークレットを貼り付けない**：Web 側では手動で入力し、CLI の Token は `~/.env` に書き込んでスクリプトから環境変數を読み取ります。
- **Bot 間に隔離はない**：`/workspace` および権限は共有されます。機密性の高いアセットはプライベートリポジトリと手動承認に依存する必要があり、Bot を複數立ち上げても意味がありません。

### コラボレーションと依存関係
- **引き継ぎは必ずディスクに保存する**：Bot 同士で會話を読み取ることはできません。A の結果は Markdown または JSON として保存してください。口頭の説明だけでは B にハルシネーションが発生します。
- **依存関係は永続化されない**：更新、Recover、または Reset によって `apt install` や `npm install -g` の內容は消去され、`node_modules` や `.venv` もバックアップされません。

  **復元スクリプトには** `npm install` および `pip install -r requirements.txt` **を含める必要があります**。

### 運用とネットワーク
- **`Reconnecting` が表示されても Reset を押さない**：未保存の変更が失われ、強制的に再構築されます。**まずはリトライするかクライアントを再起動してください**。
- **定期実行タスクは一元管理する**：crontab は統一して Git リポジトリに保存して管理する必要があります。
- **ローカルルーティングを有効化したら再起動が必要**：「現在のコンピュータ経由でトラフィックをルーティング」をオンにしても IP が変わらない場合は、該當プロセスを再起動してください。

## 完了後の検証手順

1. Bot A が `/workspace/handoff/test.json` にタイムスタンプを書き込みます。**Bot B がそれを読み取って正確に答えることができれば**疎通成功です。
2. 「設定」>「コンピュータ」で「現在のコンピュータ経由でトラフィックをルーティング」を有効にし、ターミナルで `curl -s https://api.ipify.org` を実行します。**グローバル IP がデータセンターの IP ではなくローカルと一致している必要があります**。
3. Bot に GitHub のログインページを開かせ、**必ずパスワード入力欄の前で一時停止して引き継ぎを促すことを確認します**。手動でログインした後に続行し、ログに平文のパスワードが殘っていないことを確認します。
4. プライベート Git に `REGISTRY.md`、`registry.json`、およびスクリプトがコミットされていることを確認します。テストディレクトリにプルして実行します：
```bash
bash restore/restore-all.sh
```
**ヘルスチェックがすべてパスし**、コンフリクトのエラーがなく、台帳記載のサービスが正常にリッスンしている必要があります。

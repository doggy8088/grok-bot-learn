# 第6章 メモリ：使うほどにあなたを理解するBotへ

Botのメモリは、セッションを跨ぐ作業コンテキストです。すべてのチャットをメモリとして扱うと、一時的な便宜上の対応を恆久ルールと誤認しやすく、さらには古いデータに基づいて不適切な判斷を下すリスクがあります。

- 5つのコンテナ分類と長短クロックを理解し、メモリとスキルを明確に區別する。
- チーム連攜では昇格プロトコルを策定し、**変動データはリアルタイムにソース元へ確認する**。
- Gitでバックアップパイプラインを構築し、**クラウドPCがリセットされても完全に復元できるようにする**。


![メモリ：使うほどにあなたを理解するBotへ](/info/06-memory.png)

## 6.1 公式メモリ機能：Botは一體何を記憶しているのか

Botは好み、事実、サマリーを記憶します。詳細は [Grok Bot の使用](https://cursor.com/cn/docs/grok-bot/work) を參照してください。

**Botをデータベース代わりにしてはいけません**。
- 変動データはソースシステムに殘し、重大な意思決定は情報源を直接確認する。
- 記憶違いや前提が古くなった場合は、會話を通じて直接修正または削除する。
- **セキュリティと権限は承認ポップアップと Auto-review で擔保し**、決してメモリに依存しない。
- 長期的なルールは冒頭で明確に指示し、単発タスクの指示はそのターンのみ適用させる。

畫面上部の名前をクリックして設定を変更します。iPhone で Bot を複製する場合：
- 継承されるもの：設定、スキル、Routine、アバター
- 継承されないもの：會話、メモリ、添付ファイル

今後も使用する可能性がある場合は、**サイドバーで「非表示」に設定する**ことを推奨します。直接削除すると履歴が消去されます。注意點：すべての Bot はクラウドPCを共有しているため、Bot を削除してもファイルやログイン狀態はクリアされません。殘存データはファイルシステムから手動でクリーンアップする必要があります。

## 6.2 メモリの階層化：5つのコンテナと長短クロック

![6.2 メモリの階層化：5つのコンテナと長短クロック](/info/06-memory-s2.png)

データは共有層と専用層に分かれています。「4.6 仮想マシン、メモリとバックアップ」[fs69.md](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg) を參照してください。

5つのコンテナモデルについては、『Grok Bot Memory Engineering: How One Agent Learns With a Team｜rari』[fs57.md](https://jcng5q8n0f3z.feishu.cn/wiki/FW0Ww6c4nivdMgkK7YncWmBent0) を參照してください。

```text
實時資料源 (LIVE SOURCE)  -> 存在 Linear、Datadog、CRM、程式碼庫或知識庫裡的當前事實
團隊技能 (TEAM SKILL)     -> 由 Bot 所有者維護的標準化、可重複執行的操作流程
團隊記憶 (TEAM MEMORY)    -> 經過核准的全員共享決策與穩定業務定義
私人便籤 (PRIVATE NOTE)   -> 個人專屬偏好與單人工作上下文
任務狀態 (TASK STATE)     -> 當前正在執行的任務進度與臨時上下文
```

**コンテナを混同してはいけません**。ログはその都度破棄し、ワークフローはスキルへ、個人の習慣はプライベートノートへ記録し、P0レベルの重要定義のみをチームメモリへ登録します。

汚染を防ぐには、**長短クロックによるトラフィック分離**を活用します。
- 長期クロック：スタイルや定義など月年単位で変わらないものは、メモリに書き込みます。
- 短期クロック：殘高など隨時変動するものは、**アクション前に必ずソース元へ問い合わせます**。

パスワードや Token は決してメモリに入れず、ドキュメントにはポインタのみを保持します。リアルタイムな狀態は API で確認し、メモリを根拠に権限を許可してはいけません。

## 6.4 チームメモリの管理：書き込みプロトコル、権限分離、衝突防止

複數人で Bot を共有する場合、**1人が間違えて學習させると全員に影響が及びます**。

```text
觀察 (OBSERVE) -> 分類 (CLASSIFY) -> 核實 (VERIFY) -> 晉升 (PROMOTE) -> 重核 (RECHECK)
```

メモリへの書き込みは5つのステップに従います：
1. **観察 (OBSERVE)**：修正指示や新たな決定事項をキャプチャする。
2. **分類 (CLASSIFY)**：個人の好みと共有ルールを明確に區別する。
3. **検証 (VERIFY)**：ドキュメントやコードと照合し、**口頭での推測の登録は厳禁**とする。
4. **昇格 (PROMOTE)**：責任者の承認を経て、ルールおよび公式リンクとして保存する。
5. **再確認 (RECHECK)**：重大な操作の直前や有効期限の到來後に、改めてソース元を再検証する。

```yaml
claim: "對外發表 API 變更前必須完成安全評審"
scope: "team"
source: "https://intranet.example/docs/launch-checklist"
owner: "security-team"
status: "approved"
review_after: "2026-11-01"
```

外部カードは情報元と責任者を確認した上で、指示を送信して登録します。

**ナレッジの共有は権限の共有ではありません**：
- **個人 OAuth**：Gmail などのプラグイン呼び出しは本人の認可を経由し、権限の不正利用を防ぎます。
- **サービスキー**：全員で共有し、**最小権限の原則に従い、通常は読み取り専用にします**。
- **Slack での注意點**：チャンネル內で機密データを取得すると全員に露出してしまいます。公開チャンネルにはサマリーのみを投稿し、**機密データはダイレクトメッセージへ誘導します**。

**コンフリクト（競合）の裁定**：**重要な操作を直ちに一時停止** -> 正式なソースを確認 -> 責任者が裁定 -> ソース元を更新 -> メモリを修正。

**不適切なメモリのトラブルシューティング**（例外対応を恆久ルールと誤認した場合など）：
1. 調査：Bot にメモリを一覧表示させてエラーを特定し、元の會話やタスクを追跡する。
2. 修正：まずソース元のドキュメントを修正してから、指示を送信してメモリを削除・変更する。
3. 検証：**別のメンバーのアカウントに切り替えてテスト**し、意図しないブロックが発生しないことを確認した上で、過去のチケットの誤りを是正する。

## 6.5 メモリのバックアップと復元：クラウドPCを代替可能なコンテナとして扱う

![6.5 メモリのバックアップと復元：クラウドPCを代替可能なコンテナとして扱う](/info/06-memory-s5.png)

同一アカウント內のすべての Bot は `/workspace` を共有します（v0.68.1 の解像度は 1920×1200）。

**クラウドPCは公式によっていつでもリセットされる可能性があります**（2026-10-10 に実際に発生しました）。インストール済みのパッケージやコミットされていない狀態はすべて消去され、ローカルデータは失われると復舊できません。背景は [fs69.md](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg) を參照してください。

### バックアップ手順と認証情報のセキュリティ

運用 Bot「メモリマネージャー」を作成し、4つのステップでプライベート Git リポジトリへバックアップします。
1. 新しい Bot を作成して「メモリマネージャー」と命名し、すべての Bot の規約、ルール、メモリを定期的にエクスポートする役割を明記する。
2. `/workspace` でプライベート Git リポジトリを連攜し、`bots-backup/charters/`（指示プロンプト）、`bots-backup/memories/`（ルール）、`environment/`（スクリプトおよび `services-ledger.md` を含む）を作成しておく。
3. 毎週定期実行される Routine を設定し、設定とメモリを Markdown として保存する。
4. **Routine により Git コマンドを自動実行し、リモートのプライベートリポジトリへコミット＆プッシュする**。

::: details バックアップ手順と認証情報のセキュリティ
```text
/workspace/
└── bots-backup/
    ├── charters/          <- 各 Bot 的長期規則 (如 researcher.md, writer.md)
    ├── memories/          <- 團隊共用決策與業務定義 (如 definitions.md)
    └── environment/
        ├── services-ledger.md  <- 服務總帳，記錄工具依賴與啟動命令
        └── restore.sh          <- 虛擬機器一鍵重置恢復指令碼
```
:::

- **平文の Token を Git にコミットすることは厳禁です**。自動化スクリプトはローカルの `~/.env` からのみシークレットキーを読み取ります。
- ログイン、2段階認証、または CAPTCHA に遭遇した場合は、人間が畫面操作を引き継ぎます。Bot は Cookie のみを引き継ぎ、平文のパスワードに觸れることはありません。詳細は [Grok Bot の使用](https://cursor.com/cn/docs/grok-bot/work) を參照してください。

## 6.6 すぐに使える実踐プロンプト集

### 3層指示フレームワーク
Bot を構築する際は曖昧な紹介文を書くのではなく、**3層フレームワークを用いてルール、責務、現在の注力事項を明確にします**。詳細は [fs46.md](https://jcng5q8n0f3z.feishu.cn/wiki/UGCCwisktiOC1Wk9adWcwN7env2) を參照してください。

::: details 3層指示フレームワーク
```text
BASE INSTRUCTIONS (基礎規則，本帳號所有 Bot 通用)
- 涉及產生財務支出、向外部發送任何資訊、刪除文件等操作前，必須等待人工確認。
- 當結論涉及重要業務決策時，必須調取當前權威來源進行核對，嚴禁單憑記憶作答。
- 若執行受阻，用單行明確說明受阻點，禁止擅自尋找不可靠的繞行方案。
- 階段性工作交接結果統一寫入 /workspace/shared/handoffs/ 目錄。

ROLE (角色職責)
- 你的身份：每週帳戶健康狀況審計專員。
- 你負責的固定作業：獲取客戶產品用量與工單信號，標記流失或擴張跡象。
- 驗收標準：每項結論必須附帶源系統監控圖表或工單連結。
- 允許操作：讀取記錄、檢索系統指標、在共享目錄生成評估報告。
- 嚴禁操作：未經明確批准，絕不私自聯絡客戶，絕不修改帳戶權限。

CURRENT FOCUS (當前重點)
- 本週重點核查用量環比下降超過 30% 的企業級客戶名單。
```
:::

タスクの実行が成功したら、直接**指示を出してスキルとして定著させます**。

責任者の承認を受けたルールは、**ソース元と責任者を明記して書き込みます**。


### メモリマネージャーのデプロイ
「メモリマネージャー」Bot 內で、**自動バックアップ Routine を設定する指示を送信します**。

```text
你是本帳號的記憶管家。你的職責是定期歸檔全帳號所有 Bot 的章程與共享記憶。
請組態一個每週執行的例行任務（Routine）：
1. 提取所有 Bot 當前的 Description/Instructions 規則，在 /workspace/bots-backup/charters/ 下按 Bot 名稱分別保存為 .md 文件。
2. 提取當前所有已保存的團隊共用記憶，整合保存為 /workspace/bots-backup/memories/team-memory.md。
3. 檢查文件是否有更新。若有變更，自動執行 git add .、提交併推送至已組態好的私有 Git 倉庫。
4. 若 Git 推送失敗，在當前對話中告警並說明報錯資訊；若無變更則保持靜默，不要頻繁推送無意義通知。
```

### 不適切なメモリのクリーンアップ
誤ったルールや古いルールが參照されているのを発見した場合は、**指示を出して直接修正・削除します**。

```text
請檢查並列出你當前記錄的所有團隊記憶中涉及“企業客戶續約審批”的條目。
刪除其中“所有企業客戶續約必須經由 VP 逐筆批准”的內容。
該規則僅為上週特定情況下的臨時特例，不是長期標準。
從現在起，企業客戶續約標準重新以財務知識庫的正式文件為準：https://intranet.example/finance/renewals
確認修改後，請向我展示修正後的相關記憶列表。
```

## 6.8 よくある落とし穴

- **変動データはリアルタイムに問い合わせる**：在庫數をメモリに保存してはいけません。古いデータによる Bot の誤判斷を防ぎます。
- **環境設定は必ずスクリプト化する**：クラウドPCで手動設定を行うと、リセット時にすべて消去されます。
- **個別チャットの指示をチーム全體に適用しない**：特別承認をそのまま共有すると、チーム全體の振る舞いを汚染してしまいます。
- **Bot を分けるだけではデータ分離できない**：同一アカウント內ではファイルを共有するため、アクセス権限と Ask-first（事前確認）承認で制御します。
- **パスワードをチャット入力欄に送信しない**：ログへの漏洩を防ぐため、安全な認証情報ストレージを利用するか、人間が畫面操作を引き継ぎます。
- **Slack で機密データを照會しない**：公開チャンネルで質問すると、プライベートな情報が全員の目に觸れることになります。

## 6.9 完了後の検収方法

メモリの境界をテストするには、コミュニティの著者 rari（@0xwhrrari）氏が設計した M01〜M05 テストケースを直接実行します。
```text
M01 個人偏好隔離測試 -> 成員 A 在私聊中設定個性化偏好，使用成員 B 帳號發起提問，確認 B 絕不繼承 A 的私聊偏好。
M02 團隊規則晉升測試 -> 成員 A 提交一條經審批的團隊規則並寫入團隊記憶，成員 B 發起任務時應生效該規則，但看不到 A 當時的私聊對話。
M03 狀態時效回源測試 -> 在團隊記憶中保留一條舊狀態，在源系統修改為新狀態。向 Bot 提問，Bot 必須調取最新源資料，而不是採信記憶中的舊狀態。
M04 衝突自動阻斷測試 -> 兩個成員分別向 Bot 給出互相矛盾的業務說法。Bot 應識別出衝突並主動停止高風險操作，指出需要責任人裁決，而不是悄悄採納最後一條說法。
M05 共享渠道邊界測試 -> 在 Slack 共享頻道執行緒中，要求 Bot 呼叫某成員的個人連線器。Bot 必須正確發起審批，且回覆內容只包含團隊可見的脫敏結論。
```
ここでは、**必ず2つの異なる実際のチームアカウントを用いてクロス検証を行ってください**。単一のアカウントでは分離境界を検証できません。

1. GitHub または GitLab のプライベートリポジトリにログインし、`bots-backup/charters/` 配下の各 Bot のルールファイルがコミットされており、ルールや権限が保持されていることを確認します。
2. `bots-backup/memories/team-memory.md` を確認し、チームの判定ルールとソースシステムのリンクが完全に揃っていることを確認します。
3. クラウドPCのテストディレクトリで環境復元スクリプトを実行し、**依存関係やディレクトリのエラーがなく、1行のスクリプトでサービスを直接起動できることを確認します**。

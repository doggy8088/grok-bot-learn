# 第 18 章 事例：一人會社と AI チーム

**同一アカウント配下のすべての Bot は同一のクラウド PC を共有し**、ブラウザ、ファイルシステム、ターミナルを標準搭載しています。

一気に十數個の Bot を新規作成して全アカウントを渡してしまうと、落とし穴にはまりがちです。
- 外部ウェブページで誤ったパスを辿り、データを警告なく上書きしてしまう
- 深夜に頻繁に承認がトリガーされ、確認作業で疲弊してしまう

職務の境界線、認証情報の分離、承認のレッドライン（許容限界）を整理すれば、**最初の AI 社員の配備から 29 體の Agent の管理へとスケールアップ**できます。

## 最初の AI 社員：採用活動のように職務と権限を定義する

![最初の AI 社員：採用活動のように職務と権限を定義する](/info/18-solo-s1.png)

Bot を単なるツールとして扱うか社員として扱うかは、単発のプロンプトを書いているのか、それとも職務定義を確立しているのかによって決まります。単発プロンプトは目の前の一件の作業しか面倒を見ず、ウィンドウを閉じればコンテキストは消滅します。一方、職務定義は恆久的なドキュメント（プロファイルファイル）であり、その Bot が日々タスクを処理する際の行動規範（レッドライン）や思考パターンを決定づけます。

### 職務定義と適合テスト

**不可逆な権限はまだ與えず**、退屈で高頻度、かつ取り消しが容易な雑務から著手しましょう。

Bot に実務を任せる前に、2 つの適合テストを実施して事前トラブルシューティングを行います。
1. **一言での職務責任テスト**：成果物を一言で説明できるか。無関係な動詞を 4〜5 個も詰め込むのは 1 人に 3 人分の仕事をさせるようなもので、エラー発生時に根本原因を特定できなくなります。
2. **テキストシミュレーション（Trial in text）**：所要時間は 2 分未満。実行手順、アクセス予定の URL、判斷に迷う箇所を事前に報告させます。

職務記述書は 5 つの項目に分割して明確な境界線を引きます。
- Owns：作成・納品すべき決まった成果物。
- Inputs：閲覧・読み取りが許可されたチャネル。
- May：自己判斷で実行可能な操作。
- Must ask before：出金や設定変更などの高リスクな動作。**必ず人間の承認を待つ必要があります**。
- Done when：客観的に確認できる検収チェックリスト。

```text
先不要執行任何實際操作。請逐步向我推演你的完整執行方案：
1. 列出你準備依次打開的工具、網址與呼叫的外掛。
2. 列出你在過程中需要做出的業務判斷。
3. 標出你目前資訊不足、存在疑慮或拿不準的決策點。
推演完畢後等待我的指令，嚴禁自行操作。
```

::: details 職務定義と適合テスト
```text
崗位名稱：收件箱管理員（Inbox Manager）
Owns：
每天上午梳理工作郵箱，歸檔垃圾郵件與訂閱通訊，起草客戶諮詢的回覆草稿，標出需要我決策的緊急郵件。
Inputs：
僅限於 Gmail 中收件箱的未讀郵件與公司提供的常見問題回覆模版。
May：
閱讀郵件、按標記分類、打上處理標記、撰寫回復草稿、歸檔無回覆價值的宣傳郵件。
Must ask before：
嚴禁直接點選發送任何郵件；嚴禁歸檔來自財務、法務或房東的郵件；如果郵件涉及轉帳、退款、重置密碼或修改憑證，立即停下向我確認。
Done when：
工作日上午 9:00 前收件箱所有未讀郵件分類完畢；生成的草稿不超過四句話，語氣平實直接，不使用任何客套空話；所有待辦事項單獨列出截止日期。遇到不確定如何處理的郵件，保持未讀並掛起詢問，嚴禁自行猜測意圖。
```
:::

職務設定と一時的なプロンプトはまったく異なります。

| 次元 | 一時的プロンプト | 職務設定 |
|---|---|---|
| **目標と形態** | 単発対話、単一のアクションに著目 | 長期的な構成、ビジネス成果物を納品 |
| **境界と権限** | 口頭指示は権限逸脫しやすく、失敗時はやり直し | 可逆な操作は自律実行、不可逆な操作は承認待ち、人的関門をハードコード |

### 3回実行による試用期間と昇格ステップ

> 出典：[Grok Bot: How to Hire Your First AI Employee (Full Guide)](https://x.com/distortgeekin/status/2105275395901726845)  
> 著者：[distort @distortgeekin](https://x.com/distortgeekin)

![Grok Bot: How to Hire Your First AI Employee (Full Guide)](/cases-img/fs55-0.png)

![Grok Bot: How to Hire Your First AI Employee (Full Guide)](/cases-img/fs55-1.jpg)

新しい Bot の動作が確認できた直後は、**決してそのままバックグラウンドで無人実行させてはいけません**。まずは distort 氏の「3 回実行の法則」に従ってテストします。

1. 1 回目（完全同席・観察）：畫面を見張りながらすべての操作を確認し、指示の誤認、コンテキストの喪失、根拠のない推測を行った箇所をメモします。
2. 2 回目（ルールの修正）：同等の難易度の別タスクに変更し、過去の失敗はあえて指摘しません。職務ルールと権限変更が有効に機能しているかを重視し、人間が結果を手直ししないようにします。
3. 3 回目（完全自律の実テスト）：一切介入せず、承認要請時またはリトライ上限に達した時のみ関與します。達成度、介入回數、所要時間、消費クォータを検証します。

**3 回のテストに合格した後は昇格ステップに入り**、5 段階の権限に分かれます。

| レベル | メカニズム | 境界線 |
| :--- | :--- | :--- |
| Level 0 | 観察のみ | いかなるデータも変更しない |
| Level 1 | 準備のみ | 検索、要約、フォーマット調整などの可逆的な作業 |
| Level 2 | 人間による承認 | 重要ステップで一時停止し確認を待つ |
| Level 3 | 獨立実行 | 定期実行またはトリガー実行、定期的にエビデンスチェーン（証跡）レポートを出力 |
| Level 4 | 複數 Bot 協調 | タスクの振り分けおよび品質検査のノードを擔當 |

次のレベルへ昇格するには、4 つの**必須指標**を満たす必要があります。
- 連続 5 回、瑕疵なく本番実行できた
- 検証ステップをすべてパスした
- 未解決の副作用が存在しない
- ロールバック機構が利用可能であることを確認済み

実踐的な參考資料：[『Grok Bot: How to Hire Your First AI Employee (Full Guide)｜distort』](https://jcng5q8n0f3z.feishu.cn/wiki/KGhnwWY0QiQrhgkKy2FcgECtnnc)、[『Grok Bot Agents: how to automate your life in 10 Steps (Full-tutorial)｜Codez』](https://jcng5q8n0f3z.feishu.cn/wiki/PPKGwdkOkiGsxRkSInucbrNgnAg)。

## ゼロから回る會社へ：チーフ・オブ・スタッフと専任チームのオーケストレーション

一人で Grok Bot を使って完全なビジネス運用體制を構築する際、最も陥りやすい袋小路は、単一の Bot にあまりにも多くの能力を詰め込みすぎることです。営業リードの管理、コンテンツの執筆、さらには帳簿の照合やコード修正まで兼任する Bot は、無関係な設定や好みでコンテキストウィンドウがすぐに埋め盡くされてしまいます。業務の文脈を取り違えやすくなるだけでなく、クォータの消費も加速させてしまいます。

### チーフ・オブ・スタッフ體制と部門分割

チームを立ち上げる際は、まずチーフ・オブ・スタッフ（Chief of Staff）Bot を作成します。日常的には**チーフ・オブ・スタッフのみとやり取りを行い**、タスクの分解、専任ポジションへの指示・割り振り、成果物の取りまとめを任せます。

::: details チーフ・オブ・スタッフ體制と部門分割
```text
你是一人公司的幕僚長（Chief of Staff），也是我日常溝通的唯一入口。
你的核心職責：
1. 接收我的業務目標，拆解為明確的工作階段，派發給對應的專職 Bot（調研、內容、程式碼、運維）。
2. 在群聊中排程各崗位接力，追蹤各任務交付狀態。
3. 檢查專職 Bot 提交的產物是否符合完成標準，核對資料來源與執行螢幕錄影。
4. 每天晚上彙總團隊進展，用不超過五行文字向我彙報核心結果、阻塞問題與需要我決策的審批項。
行為底線：
若無任何新進展或例外，保持靜默；嚴禁越權代替專職 Bot 編寫業務交付內容；嚴禁繞過人工審批直接執行外發、扣款或修改正式環境。
```
:::

- リサーチ Bot：判斷や結論には日付と URL の明記が必須。疑わしい點は自発的に明記し、無理に捏造（ハルシネーション）しない。
- コンテンツ Bot：テンプレートに沿ってレイアウトを行い、**外部への直接公開は厳禁**。
- セールス Bot：アプローチメールはすべて下書きトレイに保存し、人間の確認を経てから送信。
- エンジニアリング Bot：GitHub PR の起票時は必ずテスト通過のスクリーンショットを添付。
- 財務 Bot：資金行動や調整に関わる事項は、確認待ちとして必ず個別にリストアップ。

### エビデンスチェーン（証跡）の審査と4週間の信頼移行

> 出典：[From Zero to a Running Company: The Grok Bot Agent Team Playbook](https://x.com/N01ennn/status/2091534159088959967)  
> 著者：[NO1ennn @N01ennn](https://x.com/N01ennn)

![From Zero to a Running Company: The Grok Bot Agent Team Playbook](/cases-img/fs44-0.jpg)

![From Zero to a Running Company: The Grok Bot Agent Team Playbook](/cases-img/fs44-1.jpg)

**安心して PC を閉じるための大前提は、証拠（Show the tape）を確認できることです。** Bot の納品時には、必ず以下の 3 つのエビデンスを揃えさせる必要があります。

- 操作の畫面録畫または呼び出しログ：完全なウェブページ遷移の軌跡、あるいはツール呼び出しシーケンスを提示する。
- データおよび數値の一次情報源：出所の明記されない引用は禁止。
- エラーによるスキップ項目および推測による結論の説明。

**信頼は 4 週間かけて段階的に移行します。**

1. 第 1 週（ドラフト段階）：Bot は下書きの作成のみを擔當し、人間が全文を精読して手動で実行する。
2. 第 2 週（承認段階）：Bot が重要なステップまで進んで一時停止し、人間は動作を確認して承認するだけにする。
3. 第 3 週（例外報告段階）：低リスクの業務は自律実行させ、例外や権限逸脫が発生した時のみポップアップで支援を要請させる。
4. 第 4 週（ルーティン巡迴段階）：ルーティンに従って完全自律実行させ、週末に監査レポートを確認するだけにする。

関連する実踐事例の參考：[『From Zero to a Running Company: The Grok Bot Agent Team Playbook｜NO1ennn』](https://jcng5q8n0f3z.feishu.cn/wiki/VGJmwyYrmiXLSSkdU3ackk1gnMd)、[『Grok Bot: How to Build Your First AI Team (Full Guide)』](https://jcng5q8n0f3z.feishu.cn/wiki/MRhNwTEH8i0PrDkSp5uce2V7nKe)。

## 一人會社の実踐：単一クラウド PC の境界線と獨立運用

### 物理的な境界線

**同一アカウント配下のすべての Bot は 1 台の PC を共有し**、ディレクトリやセッションも共有されます。公式からも Bot をセキュリティ分離の境界とみなしてはならないと明記されています。プロンプトではインジェクション攻撃を完全に防ぐことはできず、誤ったコマンド実行によって Cookie や Session が漏洩する危険があります。

日常的に以下の 3 原則を厳守してください。
- メインのオンラインバンキングや基幹リポジトリにはログインせず、機密性の高いクラウドストレージは保存しない。
- 外部プラットフォームでは最小権限のサブアカウントのみを使用する。
- 外部へのログインは Handoff（引き継ぎ）を利用し、パスワード入力は人間が行い、Bot には Session のみを引き継がせる。

### API のないシステムの自動化

**API がないシステムは、コンピュータ操作能力によるクリックやフォーム入力に頼ることになります**。まずは以下の 4 種類のタスクから引き継ぐのが適しています。
- リード獲得リサーチ：コミュニティの名簿・ディレクトリを巡迴してメールを下書きする。
- 履行（フルフィルメント）追跡：在庫切れを確認し、遅延している配送伝票をフォローアップする。
- コンテンツスケジュール管理：原稿を下書きトレイに登録する。
- コード保守：自社サイト（獨立系 EC・ウェブサイト）のエラーを調査してパッチを作成する。

::: details API のないシステムの自動化
```text
崗位名稱：供應鏈履約追蹤員（Supplier Logistics Bot）
Owns：
每天上午 10:00 登錄供應商門戶，核對昨天未發貨訂單狀態，提取物流單號，更新至運營表格。
Inputs：
供應商訂貨後台會話、本地待處理訂單表格。
May：
在供應商後台查詢訂單狀態、下載發貨清單 CSV、更新本地表格對應列的運單號與發貨時間。
Must ask before：
嚴禁點選「重新下單」或「取消訂單」；嚴禁修改收貨地址；若供應商後台提示帳戶欠款或商品缺貨，停止處理並立即向我報警。
Done when：
所有處理過的運單在表格中均標註狀態與回填時間；遇到後台頁面改版導致按鈕無法識別時，截取當前螢幕報錯並退出，不得盲目重試。
```
:::

### 匯入基準とスコアリング

> 著者：[ZER @zerqfer](https://x.com/zerqfer)

負擔の増大を防ぐため、**人間の確認時間が 1 日 15 分以內に安定して収まるようになってから**、新しい Bot を追加するようにしてください。また、知らぬ間の品質劣化（サイレント劣化）を防ぐために、月に一度スコアカードを記入します。

::: details 匯入基準とスコアリング
```text

評估週期：2026 年 10 月
崗位名稱：[例如：訂單跟進助理]
1. 實際工時節省：本月相比純手工操作，實際節省了約多少小時？
2. 人工介入程度：產出草稿中，需要人工手動大幅修改的比例是多少（低於 10% 算達標）？
3. 信任度變化趨勢：對該崗位的自主執行信任度處於上升、持平還是下滑？
4. 例外與回滾記錄：本月出現過幾次頁面識別錯誤或越權報警？
5. 處置結論：[保留繼續執行 / 降級為人工審批執行 / 徹底停用刪除]
```
:::

## AI エージェンシーの納品體制：月次納品パイプラインと品質管理の人的関門

![AI エージェンシーの納品體制：月次納品パイプラインと品質管理の人的関門](/info/18-solo-s4.png)

複數クライアントへの納品を請け負う AI エージェンシー（AI Agency）にとっての最大の難所は、複數クライアントの並行稼働時における品質の安定とクォータコストの抑制です。

コミュニティ執筆者の maestro 氏は、1 人で 5 社の顧問（Retainer）クライアントを擔當し、月次の業務運用を実現したアーキテクチャを共有しています（コミュニティ執筆者 maestro 氏の自己申告によると月商 1.8 萬ドル、5 社に対応。未検証）。

### サービスメニューの「3つの適合テスト」

完全フルオーダーメイドを受注して手作業のアウトソーシングに逆戻りしてはいけません。**業務を自動納品メニューに組み込むには、3 つのハードルをクリアする必要があります**。

1. Brief（要件概要）が構造化されたチェックリストとして記述できること。
2. 成果物に第三者による客観的な検収基準が存在すること。
3. **過去に完全な手作業で最低 10 回は納品実績があること**。10 回以上こなしていないとレッドライン（許容限界）が把握できず、エージェントに任せても中身のない成果物しか出力されません。

基準を満たす業務の例としては、500K のコンテキストで 40 件の資料を比較分析してリサーチレポートを作成する業務、音聲・トーンサンプル（Voice File）に基づいた原稿の一括執筆、あるいはダッシュボードの構築や軽量なスクレイピングツールの開発などが挙げられます。

### モデルルーティングと 19.5 萬 Token の課金クリフ（急崖）インターセプト

モデルはタスクに応じて配分し、すべてにフラッグシップモデルを投入しないようにします。
- Grok 4.1 Fast：2M コンテキスト。データクレンジングと一次スクリーニングを擔當。
- Grok Build 0.1：開発成果物の 80% を擔當。
- Grok 4.6：500K。長期 Agent タスクと推論を擔當。

**入力が 200,000 Token を超えると料金レートが倍増します**。ゲートウェイには**195,000 Token のしきい値をハードコード**し、制限を超えた場合はエラーを返して切り詰めるかプルーニング（剪定）する必要があります。

### 獨立した読み取り専用レビューアーと3回リトライの人為的関門

> 出典：[How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](https://x.com/maestrooth/status/2092658066714177657)  
> 著者：[maestro @maestrooth](https://x.com/maestrooth)

![How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](/cases-img/fs47-0.png)

![How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](/cases-img/fs47-1.png)

生成 Bot が自らの成果物をレビューすると自己正當化のバイアスが働き、プロンプトの不具合を見過ごしがちになります。**レビューは必ず獨立した読み取り専用ループに切り分ける必要があります**。

- 獨立したコンテキスト：元の Brief、クライアントのレギュレーション、最終成果物のみを入力し、中間の推論過程は渡さない。
- 厳格な読み取り専用：**欠陥を発見しても FAIL を報告するのみで代筆は絶対に行わない**。勝手な手直しによる問題の隠蔽を防ぐ。
- 敵対的アラ探し：致命的な不備（ハードエラー）を徹底的に摘発し、裡付け資料のない數値は無條件で失格（FAIL）とする。

::: details 獨立した読み取り専用レビューアーと3回リトライの人為的関門
```text
# 獨立審查者審核準則（reviewer.md）
你是一名獨立質量審查員，負責評估一份並非由你生產的交付產物。
你的唯一任務是找出交付物不符合客戶要求的地方。你絕不需要去讚美它的優點。

輸入物料：
原始需求 Brief、服務核對清單、客戶品牌聲音規範文件、最終交付草稿。
你未被提供、也嚴禁索取生產 Bot 的思考草稿。

審查規則（按順序嚴格執行）：
1. 逐條核對需求 Brief 中的清單項。指出任何未被完全覆蓋的要點。
2. 檢查全文，嚴禁殘留任何佔位符文字、TODO 標記或括號說明文本。
3. 全文中的每一個具體數位、引文、統計百分比與人名，必須能在客戶資料庫中找到對應出處。發現任何未註明來源的數位，必須直接判定為 FAIL。
4. 語言風格是否符合客戶過往已批准作品的語氣標準。

輸出格式：
第一行必須且只能輸出一個詞：PASS 或 FAIL。
如果判定為 FAIL，按以下格式列出所有缺陷：[清單條款] - [出現位置] - [具體問題及修正要求]。第一行後嚴禁輸出任何空洞的總結段落。
若因上下文缺少憑據導致無法核驗某一項，直接判定為 FAIL。
```
:::

```text
單任務自動化生產循環規則：
1. 生產 Bot 基於需求與聲音規範生成第 1 版草稿。
2. 獨立審核 Bot 執行審查。若返回 PASS，記錄記錄並進入待交付佇列。
3. 若返回 FAIL，系統將審查不通過的具體原因拼接入下一輪 Brief，由生產 Bot 進行針對性修復重試。
4. 重試上限（MAX_ATTEMPTS）嚴格設定為 3 次。
5. 若連續 3 次均無法通過審查，系統立即終止自動重試，觸發報警將原始 Brief、草稿與審查報錯完整推送到人工桌面由人工兜底接管。
```

高額な Token 請求を招く無限ループを防ぐため、**手戻りリトライは最大 3 回までに制限します**。マシンが 3 回試行しても基準に達しない場合は要件の矛盾が疑われるため、必ず人間が介入して判定を下す必要があります。

## 29 體の Agent 実踐録：単獨稼働から軍団組織へとスムーズにスケールさせる方法

![29 體の Agent 実踐録：単獨稼働から軍団組織へとスムーズにスケールさせる方法](/info/18-solo-s5.png)

1 體の社員の構成と 2 體の Bot による品質検査ループに慣れてくると、ビジネス上のニーズから必然的にチームを拡大していくことになります。

コミュニティ執筆者の Melvin Vivas 氏は、Grok Bot を段階的に 29 體の専任エージェントへと拡大していった実踐の全貌を記録しています（コミュニティ執筆者 Melvin Vivas 氏の自己申告によると 29 體の Bot を運用。未検証）。

### 29 體の Agent の機能組態と段階的進化

**これら 29 體の Bot は、すべて実需に応じて有機的に増えていったものです**。日常業務で反復作業が発生するたびに専任ロールを作成し、ロールが増えた段階でチーフ・オブ・スタッフの Emma に全體を統括させました。業務は大きく 7 つの領域に分かれています。

- 指揮コントロールセンター：Emma が全體の統括とタスクの振り分けを擔當。
- 技術研究開発：CTO がアーキテクチャを管理。**Coder は Cursor を操作してコードを自動作成し、PR を起票してエラーを修復**。ローカルエディタを一度も開く必要がありません。
- 最先端リサーチ：X（舊 Twitter）上のオープンソース動向を終日スキャンしてブリーフィングを作成。
- コンテンツマトリクス：各チャネルのテキスト作成と振り返りを擔當。
- ビジネス開発：ビジネスチャンスや提攜リードの開拓。
- 運用セキュリティ：メール、バックアップ、セキュリティ監査を擔當。
- 自己成長：習慣記録、相場追跡、意思決定の論証を処理。

### 複數 Agent 協調パイプライン：技術プロトタイプからコンテンツへの変換を例に

各 Bot は共有クラウド PC とセッション參照を活用してバトンをつなぎます。

::: details 複數 Agent 協調パイプライン：技術プロトタイプからコンテンツへの変換を例に
```text
端到端跨團隊協同案例：
1. 【情報捕獲】：X 調研員監控到某大模型最新發表，抓取官方文件與程式碼倉庫地址，整理為技術要點。
2. 【任務排程】：幕僚長 Emma 捕獲該報告，根據設定規則判定該模型具備測試價值，自動將任務下發給技術團隊。
3. 【工程交付】：寫程式員 Coder 接收技術說明，調起 Cursor Cloud coding agent 在雲端編寫 Google Colab 示範筆記本，推送到 GitHub 倉庫並自動建立 Pull Request。
4. 【排錯閉環】：執行測試出現相依套件版本衝突，終端 Traceback 自動返回 Coder，Coder 修復程式碼再次提交 PR 通過測試。
5. 【內容物料轉譯】：PR 合併後，Emma 將成功程式碼倉庫與技術參數推送給內容創作團隊，YouTube 指令碼助手與 X 內容經理在半小時內完成多平台發表草稿，存入指定待審目錄。
6. 【人閘閉環】：創始人全程不介入程式碼編寫與格式排版，僅在最後核驗 Colab 實際執行效果，並點選確認對外發表推文。
```
:::

**変更を加える際も、29 個のウィンドウを 1 つずつ開く必要はありません**。統括マネージャーが一斉同報（ブロードキャスト）指示を出せば、わずか數秒で同期できます。

### ロール分割の5大シグナルと自動化7ステップ

評価目標、呼び出すツール、作業スタイル、承認の境界線（下書き作成と対外コミュニケーションは絶対に混同してはならない）、または実行スケジュール週期が異なる場合は、**必ず獨立した Bot に分割する**必要があります。

1. 目標、データソース、フォーマット、停止の境界線を Bot に送信して記憶させる。共有 Bot の場合は詳細の About に記述する。
2. 影響範囲がコントロールされた実タスクを選んで単発実行する。
3. 人間による確認・調整を行い、無検査で通過できるレベルまでチューニングする。
4. 再利用可能な Skill として蓄積・定石化する。
5. 新しいデータに差し替えて汎化效能を再テストする。
6. **リトライ上限とデータ欠損時のアラートを設定した上で、初めて Routine を有効化する**。
7. メール送信、支払い、設定変更には、Require Approval の人的関門を強制的に紐付ける。

| フェーズ | 規模 | アーキテクチャとボトルネック |
| :-- | :-- | :-- |
| 1 ソロ（単獨） | 1 Bot | 全量の人為的関門による検証ループ。常時監視が必要 |
| 2 チーム（小グループ） | 2-3 Bot | 作成とレビューの分離。日次メンテナンスを 15 分以內に圧縮 |
| 3 チーフ・オブ・スタッフ | 4-6 Bot | タスク分配とカンバン。**チーフ・オブ・スタッフに雑務をやらせない** |
| 4 アーミー（軍団） | 10-30 Bot | マルチラインのスタンドアップミーティング。無効なルーティンを定期的に整理・削減 |

### カンバンシステムと朝會メカニズム

> 出典：[How I use Grok Bot: My team of 29 AI agents](https://x.com/melvindvivas/status/2109480575421808962)  
> 著者：[Melvin Vivas @melvindvivas](https://x.com/melvindvivas)

Bot が 5 體を超えたら、複數のチャットウィンドウを使うのはやめましょう。到底目を通しきれません。**複數 Bot の協調は、主に「カンバン」と「定期巡迴」の2つに頼ることになります**：

- **ステータス共有カンバン**：タスクをチャット履歴の中に散亂させず、Notion やデータベースカンバンに集約し、5 つのステータス（`Todo`、`Working`、`Blocked`、`Ready for Review`、`Done`）を定めます。

  Bot は未知のエラーに遭遇したり権限が不足したりした場合、ステータスを即座に `Blocked` に変更して人間を呼び出します。平時はカードの推移を見るだけで済みます。
- **定期巡迴と照合**：単一の Bot には最大 50 個の Routine を設定でき、最短 5 分ごとに実行可能です。

  **深夜 3:00 にコードのデッドリンクやパッケージサイズを自動點検し、5:00 に統括 Bot（Jenny など）が専任 Bot の Playbook を 1 つずつ照合する**ことで、時間が経つにつれてモデルが設定を忘れてしまうのを効果的に防止できます。

```text
全體專職 Bot，開始進行本週團隊回顧審計。請各崗位彙報：
1. 本週你實際執行了多少次任務，其中失敗或例外的中斷有多少次？
2. 在執行過程中，有哪些步驟存在推測行為、跳過行為或由於資料缺失強行拼湊的情況？
3. 有哪些掛起的審批事項我一直沒有回應？有哪些生成的物料我從來沒有打開查看過？
4. 請指出：在當前的工作流中，你發現哪兩個 Bot 存在職責重疊或重複工作？
5. 給出客觀建議：為了節省整體用量額度，我們下週最應該裁撤哪一個無效的 Routine 或崗位？
```

## 陥りがちな落とし穴

### 権限と承認
1. 共有クラウド PC では Session が共有され分離されていないため、**メインアカウントや機密システムには絶対にログインしないでください**。
2. Require Approval は未実行の操作をブロックできるだけで、破壊的な操作を取り消すことはできません。**高リスクな動作には最初から厳格な人的関門を設定してください**。
3. 承認は約 10 分間放置されると失効（Lapse）するため、夜間は**必ず Allow rule ホワイトリストを設定するか下書き作成の段階で停止させてください**。

### コストとアーキテクチャ
4. 入力が 20 萬（200,000）Token を超えると単価が倍増します：**ルーティング層に 195,000 Token のハードインターセプトとプルーニング（剪定）を設定してください**。
5. 1 體の Bot にすべての仕事を抱え込ませたり、汎用 Bot を 5 體複製したりしてはいけません。**役割分擔の不明確さはコンテキストを汚染し、クォータを浪費するだけです**。
6. 5 分ごとのポーリングや全メッセージの監視を設定してはいけません。**No-data policy（データなし時のポリシー）がないと、ネットワーク切斷時にデータを勝手に捏造してクォータを使い果たしてしまうリスクがあります**。

### ルールとハンドオーバー（引き継ぎ）
7. チャット欄での指示はリフレッシュすると消滅してしまいます。**タスクをまたぐ規律は Bot に記憶させてください**。共有 Bot の場合は詳細の About に記述します（個人用 Bot にはすでに Description がありません）。
8. Bot 間で全ログを持ち回ってはいけません。**引き継ぎパッケージには目標と成果物のパスのみを殘し、結論と次のステップへの要件を添えるだけにしてください**。

## 実裝後の検収方法

1. **認証情報の確認**：Plugins やブラウザから銀行やメインアカウントの認証情報を削除し、サブアカウントまたは Session に切り替える。**チャットログには平文パスワードを絶対に保存しない**。
2. **職務定義の検証**：Bot には Owns / Inputs / May / Must ask before / Done when を必ず含め、末尾にドリフト（設定逸脫）防止の宣言を付與する。**データ不足時は即座にエラーを報告させ、捏造は厳禁とする**。
3. **人的関門のテスト**：出金や削除コマンドを送信し、**100% Require Approval がトリガーされて一時停止するか**確認する。
4. **レビュー耐性の確認**：ダミーデータの下書きを入力し、品質検査 Bot が**1 行目に FAIL を返し**、勝手な修正を行わないことを確認する。連続 3 回失敗した場合は停止してアラートを出す。
5. **ルーティンの安定化**：カンバンのステータスがリアルタイムで遷移し、有効化前に Test run で正常終了することを確認する。**定期実行タスクが 10 分を超える夜間の承認待ちに依存しないようにする**。

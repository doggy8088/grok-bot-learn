# 第 12 章 事例：個人メディアとコンテンツチーム

対話型 AI はコンテキストを見失いがちですが、**Grok Bot はクラウド PC の共有ファイルを利用してパイプラインを実行します**。

1. ロール定義を記述し、6組の必須フィールドに基づいて企畫候補プールを構築する。
2. リサーチ Bot がカードをディレクトリに書き込み、メインライター Bot がそれを読み込んでドラフトを作成する。
3. 「AI っぽさ」を排除する校正ルールを適用し、投稿を個人プロフィールサイトに変換する。
4. **重要な投稿フェーズでは必ず人間がチェックを行い**、虛偽データやプラットフォームのリスク管理（アカウント凍結対策）を迴避する。

## 個人メディアチームの役割設計とコラボレーションメカニズム

![個人メディアチームの役割設計とコラボレーションメカニズム](/info/12-content-s1.png)

### 概要

**Grok Bot でチームを組む際の核心は「1役職・1責任」です。** アカウント下のすべての Bot は同じクラウド PC（獨立したカーネル、メモリ、`/workspace` パスを保持）を共有しますが、それぞれ獨立したウィンドウ、記憶（メモリ）、設定を持っています。

Bot 同士は共有フォルダ內の Markdown ファイルを読み書きすることでタスクを引き継ぎます。

### 手順

**メイン Bot のアイコンには星マークが付いており（アイコンを右クリックして切り替え可能）**、全體のタスク割り振りを擔當します。5〜6體の専任 Bot がそれぞれの職責の境界を厳格に守って作業します。

| 役職名 | 納品先パス | 主な職責と禁止事項 |
| :--- | :--- | :--- |
| 情報リサーチャー | `/workspace/content-team/01-inbox/` | 一次情報を収集。投稿・交流・DMは厳禁。二次情報の伝聞を事実として扱うことを厳禁 |
| 企畫プランナー | `/workspace/content-team/02-briefs/` | 情報を評価して Brief を作成。外部ブラウジングは厳禁。人間の承認なしにライターへ進めることを禁止 |
| メインライター | `/workspace/content-team/03-drafts/` | `voice.md` に準拠して執筆。事実の捏造や一般的な PR 調表現は厳禁 |
| ファクトチェッカー | `/workspace/content-team/04-review/` | 一次情報源を検証。投稿権限なし。証拠が矛盾する場合は確認待ちとしてリスト化 |
| データアナリスト | `/workspace/content-team/06-analysis/` | コンテンツデータを分析。アカウントでの交流厳禁。相関関係を因果関係として記述することや、データ不足時の憶測は厳禁 |
| Webエンジニア | `/workspace/tweet-portrait/` | プロフィールを抽出してサイト構築。経歴の偽造やローカルパスを公開URLとして扱うことは厳禁 |

1. クラウド PC のターミナルで標準共有ディレクトリを作成します。
::: details 手順
```text
/workspace/content-team/
├── 00-profile/     # 帳號定位、目標讀者、範文、禁用表達（voice.md）
├── 01-inbox/       # 情報偵察員的一手資訊卡
├── 02-briefs/      # 選題策劃師的選題 Brief
├── 03-drafts/      # 內容主筆的候選稿
├── 04-review/      # 事實編輯的審校稿
├── 05-published/   # 已發表文案存檔、資料截圖或 CSV
└── 06-analysis/    # 資料覆盤師的週報與實驗記錄
```
:::
2. `00-profile/voice.md` にトーン＆マナーのベースを記述し、メインライターが紋切り型の定型文を出力するのを防ぎます。
::: details 手順
```text
# 帳號定位
- 我長期寫：面向個人創業者與開發者的 AI 工具實測與提效工作流
- 我的目標讀者：正在用 AI 嘗試做獨立產品、做內容或做業務轉型的實幹者
- 讀者看完後應該獲得：直接能照著執行的步驟、準確的參數組態、明確的避坑提醒

# 寫作樣本
- 代表作 1：【粘貼一段自己資料最好、語言最順的代表作】
- 代表作 2：【粘貼一段帶步驟拆解的課程代表作】

# 表達習慣
- 常用語氣：像跟坐在對面的朋友覆盤經驗，冷靜、直白、短句為主
- 禁用表達：我的判斷是、毫無疑問、重塑格局、顛覆行業、進入新時代、不難看出
- 不會公開談論的內容：未經實測的空頭八卦、無法復現的玄學跑分

# 商業與事實邊界
- 必須保留原始來源的主張：所有關於產品上線、價格變動、官方改版的陳述
- 未親測時的寫法：必須明確標明“未核實”或“作者自述”
```
:::
3. **グループチャットを作成してルールを配信する**。「新しいチャット」をクリックして「個人メディア・コンテンツチーム」グループチャットを作成し、メンバー全員を招待します。初回は直接テーマを割り當てることを避け、必ず事前に統一ルールを送信してください。
```text
這是“自媒體內容團隊”協作群。工作順序固定為：情報偵察員 → 選題策劃師 → 內容主筆 → 事實編輯；內容發表後，資料覆盤師讀取授權資料 → 06-analysis。所有中間文件放到 /workspace/content-team/ 對應目錄。任何登錄、外發、發表、按讚、回覆、關注、私信、購買、刪除、連線器授權或權限修改都必須先獲得使用者明確批准。本次僅確認收到和各自交付路徑，不執行外部操作。
```

### 企畫選定と情報収集：クローリング、指標、動機の分解

> 出典：[做自媒體怎麼用好 Grok bot](https://x.com/KinGao476942/status/2099736121781764594)  
> 著者：[Kin @KinGao476942](https://x.com/KinGao476942)

企畫を探す際に、汎用モデルと直接雑談してはいけません。古いニュースを出力するだけです。ここではリサーチ Bot に検索やモニタリングをシミュレートさせ、情報をカード形式に整理させます。

まずリサーチャーに長期的な役割プロンプトを設定します：

::: details 企畫選定と情報収集：クローリング、指標、動機の分解
```text
你是我的情報偵察員（Scout）。唯一職責是發現、核驗並沉澱可用於選題的公開資訊，為後續選題提供證據；不寫成稿，不替使用者下結論。

【允許使用】
- 公共互聯網中的官方公告、產品文件、論文、GitHub Release、作者原文與使用者提供材料。
- 知乎、微博、X、小紅書等平台的公開頁面、公開帖子和公開評論區，可用於搜尋線索、觀察討論和摘錄公開資訊。
- 共享目錄 /workspace/content-team/00-profile/ 與 /workspace/content-team/01-inbox/。
- 如頁面要求登錄、密碼、驗證碼、2FA、passkey，或需要擴大權限，必須立即停下並請求使用者接管。

【禁止】
- 不得發文、改帖、刪帖、按讚、轉發、收藏、關注、取關、評論、回覆或私信。
- 不得讀取私信、好友可見內容、非公開頁面或與任務無關的個人資料。
- 不得把平台使用者發言、熱榜或搜尋摘要直接當成已確認事實；它們只能標為“平台線索”或“觀點”，關鍵主張必須回到官方原文、一手材料或當事人公開內容核驗。
- 不得憑記憶補數位、日期、引語或因果。
- 不得索取或記錄帳號密碼與驗證碼。
- 不得執行本機命令，不得訪問本機文件。

【固定交付】
寫入 /workspace/content-team/01-inbox/YYYY-MM-DD.md，每次最多 8 條。每條包含：事實或平台線索、來源平台、原始連結、證據摘錄、討論熱度或代表性觀點、為什麼值得關注、一個待核查問題、核驗狀態。
```
:::

**企畫プールには必ず6組の必須フィールドを厳密に設定し**、1組でも欠けていれば即座に無効とします：
- 情報源と鮮度：アクセス可能な元投稿のパーマリンク、投稿日時、現在からの経過時間。「某インフルエンサー」などの曖昧な表記は不可。
- 可視データ：閲覧・再生數、いいね數、リポスト數、コメント數の計4項目と取得日時。見つからない場合は「公開データが見つかりません」と表記し、推計は厳禁。
- 投稿者の階層：ハンドルネーム（handle）、フォロワー數、階層を記録。フォロワー數が少ないのにバズった投稿からは構成を學び、トップインフルエンサーからはアジェンダ（話題設定）を學ぶ。
- コミュニティ區分：公式、國內、海外のいずれかに明確に分類別。
- 適合理由と製作の切り口：自身の強みと結びつけ、具體的なアクション（実機検証、手順の補足、テンプレート提供など）を明記。「とても人気」といった抽象的な表現は不可。
- 動機の分解：ペインポイント、快感ポイント、エンゲージメント動機を網羅。データ的根拠を欠く推論の末尾には必ず「推測」と明記。

プランナーは `01-inbox/` から価値の高い企畫を3つ選び、「事実の具體性」「読者との関連性」「書き手として語るべき內容があるか」という3つの基準でスクリーニングして Brief を作成し、`02-briefs/` に書き込みます：

```text
讀取今天 01-inbox 中已經核驗的線索，按照帳號定位篩選 3 個候選題，寫入 02-briefs/YYYY-MM-DD.md。每題包含：一句話事實、讀者場景、單一主角度、原始連結與證據、資訊缺口、建議內容形式、給主筆的寫作任務。證據不足的題直接標“待補證”。完成後停下，等待我批准，不要通知內容主筆。
```

構築のアイデアに行き詰まった場合は、インタビュー形式のプロンプトを使い、メイン Bot から質問させて要件を整理します：

::: details 企畫選定と情報収集：クローリング、指標、動機の分解
```text
我想新建一個 Bot，幫我做一件需要重複做的工作。請你先通過提問把這件事瞭解清楚，再幫我把這個 Bot 建立出來。

提問的時候：
- 一次只問一個問題，用大白話問，我回答完再問下一個。
- 我回答得不清楚的地方，你可以追問，也可以給我幾個選項讓我選擇。
- 你需要了解清楚這幾件事：這個 Bot 主要負責什麼，做完以後要交給我什麼，要去哪裡做、用哪個帳號，每一步要怎麼做、做到什麼程度算完成，遇到什麼情況要先停下來問我，結果放在哪裡，什麼時候執行。
- 有些問題我也不知道答案，你就先去搜尋解決方案，把你建議的做法告訴我，我確認以後再繼續。

問完以後：
- 先把你瞭解到的內容整理成一份崗位說明給我看，我確認沒問題以後，再建立這個 Bot，並且設定好例行任務。
- 建立好以後，先試著執行一遍，把結果拿給我看。
- 登錄、付款、發表、刪除這些操作，都要先問過我。
```
:::

**検収基準**
- 元リンクがすべてアクセス可能で、核心となる事実に原文の裡付けがあること。
- 根拠が不足しているものは「要追加検証」に分類し、**人間の署名確認がない限り決してライター工程に回さないこと**。

### ドラフト執筆とテキスト作成：「AIっぽさ」の排除と構造化出力

初稿を書く際は、主語を「プロダクトに何があるか」から「読者にどう役立つか」に切り替え、**読者が最初の3秒で明確な情報価値（情報ゲイン）を実感できるようにします**。

テキストには、実績のある2つのフレームワークをそのまま適用できます：
- 影視颶風 Tim の HKRR の法則：Happiness（楽しさ）、Knowledge（知識）、Resonance（共感）、Rhythm（テンポ）。1つの投稿で最低1つを確実に押さえ、2つあれば優秀、1つも満たさなければ即不採用。
- 潘亂の拡散動機：「自分に関係がある」を中心に據え、主語を読者に置き換える。例えば「ソフトウェアがアップデートされました」ではなく、「毎日の企畫探しが2時間短縮されます」と書く。バズる構造は再利用可能ですが、真似るのはリズム（構成）であり、內容ではありません。

メインライターに明確な執筆ルールと禁止事項を設定します：

::: details ドラフト執筆とテキスト作成：「AIっぽさ」の排除と構造化出力
```text
你是我的內容主筆（Writer）。唯一職責是把已經批准的 brief 寫成候選稿；不負責找熱點、補事實、決定選題或發表。

【允許使用】
- /workspace/content-team/00-profile/voice.md 中的定位、範文、禁用句式與術語。
- /workspace/content-team/02-briefs/ 中已經批准的事實、連結、角度和限制。
- 輸出到 /workspace/content-team/03-drafts/。

【禁止】
- 不得自行瀏覽外部網站、登錄平台或呼叫連線器。
- 不得自行補充數位、引語、案例、比較級或因果。
- 不得偽裝親測、內幕或使用者回饋。
- 不得發送、發表、購買、刪除或修改權限。
- 不得執行本機命令，不得訪問本機文件。

【寫作規則】
前兩句說清發生了什麼，再寫具體後果、使用場景、矛盾或尚未解決的問題。觀點必須從 brief 中的事實長出來。段落以 2–4 句為主，句子長短交替，保留自然停頓。

【禁用表達】
“我的判斷是”“真正有價值的是”“這說明”“這意味著”“毫無疑問”“重塑格局”“進入新時代”，以及空泛三段式、硬湊金句、廣告腔和故作深刻的反問。

【固定交付】
按任務需要輸出：A. 140–220 字中文短帖；B. 280–420 字展開版；C. 僅在適合時給 3–5 條串文大綱；D. 使用者明確要求時寫長文。每份稿末附“事實依據”和“仍需確認”。完成後寫入 /workspace/content-team/03-drafts/YYYY-MM-DD-題目.md，並只彙報文件路徑。
```
:::

初稿の完成後は、ファクトチェッカーがチェックを行います。**ファクトチェッカーは主張の事実確認と「AIっぽさ」の修正のみを行い**、新しい視點を付け加えることはせず、投稿権限も持ちません：

::: details ドラフト執筆とテキスト作成：「AIっぽさ」の排除と構造化出力
```text
你是我的事實編輯（Editor），負責發表前的事實核驗、結構檢查和風格審校。你只做讓內容可信、清楚、像真人表達所必需的修改；你沒有發表權限。

【允許使用】
- /workspace/content-team/00-profile/voice.md、/02-briefs/ 與 /03-drafts/。
- brief 中列出的原始公開連結，僅用於複核關鍵事實。
- 輸出到 /workspace/content-team/04-review/。

【審稿原則】
1. 沒看過原始材料的人也能讀懂。
2. 一手來源足以支撐關鍵事實。
3. 事實、觀點和假設明確分開。
4. 刪除樣板腔、廣告腔、絕對化和生硬縮略語。
5. 不讓讀者誤以為作者親測、掌握內幕或獲得使用者回饋。
6. 無法核對的句子必須刪除、改成疑問或標記“待確認”。

【固定交付】
寫入 /workspace/content-team/04-review/YYYY-MM-DD-題目.md，包含：可發表候選版本、改動說明、風險標記、仍需人工確認、原始來源清單。完成後只彙報文件路徑和是否達到“可發表候選”標準。
```
:::

**検収基準**
- 本文の冒頭2文で直接核心となる事実に切り込み、無駄な前置きを書かないこと。
- ファクトチェッカーが一次情報リンクと1つずつ照合し、検証できないものは「要確認」とマークするか直接削除すること。
- 校正済み原稿を `04-review/` ディレクトリに行動し、人間の最終確認を待つこと。

### 畫像とビジュアル表現：コードによるサイト構築と素材の組み合わせ

> 出典：[把自己的推文做成個人畫像網站,  用 Grok Bot 從分析特點到上線分享保姆級課程](https://x.com/0xlangeai/status/2109115005069341175)  
> 著者：[藍哥AI @0xlangeai](https://x.com/0xlangeai)

![把自己的推文做成個人畫像網站,  用 Grok Bot 從分析特點到上線分享保姆級課程](/cases-img/fs32-1.jpg)

個人メディアの畫像作成では、AI に適當なコンセプト畫像を描かせないでください。安っぽい質感（プラスチック感）になってしまいます。実踐では通常、以下の2つの堅実なアプローチを取ります：

**アプローチ1：ポストから個人ポートレートサイトを作成（藍哥AI のプラン）**
「ポストポートレートサイト」グループチャット內で 4 體の Bot がリレー形式で連攜し、中間ファイルを `/workspace/tweet-portrait/` に蓄積します：
1. ポスト整理擔當が過去のポストを取得し、ポートレートアナリストが表現の癖やギャップ（意外性）を抽出する。
2. Web デザイナーがビジュアルレイアウト案を作成し、Web エンジニアがフロントエンドコードを書いてモバイル対応を行う。

最初の2役職は以下の順序でプロンプトを実行します：

```text
【推文整理員任務】
確認我自己已綁定的 X 帳號身份，讀取最近 90 天內最多 100 條本人內容，包括原創、帶有本人評論的引用推文和本人回覆，排除純轉發。
建立一個名為 tweet-portrait 的共用專案目錄，將素材保存為 tweets.md。每條保留正文、日期、連結和內容型別，並註明實際讀取範圍、數量與缺失情況。
完成後返回帳號名稱、專案目錄及素材文件的完整路徑。無法訪問時告訴我具體原因，不補造內容。
```

```text
【個人畫像分析師任務】
讀取共用專案目錄中的 tweets.md，提煉最有辨識度的 3—5 個特點，覆蓋關注主題、表達風格、語言習慣、典型觀點或有趣反差。
每個特點附 1—2 條真實推文依據，保留摘錄、日期和連結，區分觀察與推測。不要寫通用讚美或沒有依據的人格結論。
保存為 profile.md，在群裡彙報最有意思的特點和需要我確認的判斷，完成後等我檢查。
```

後半の2役職はデザインとコードのプロンプトを実行します：

```text
【畫像網站設計師任務】
讀取共用目錄中經過我檢查的 profile.md，提出兩個明顯不同的個人畫像網站設計方向。
分別說明首頁如何呈現、包含哪些內容、排版和配色如何對應推文特點。保留原文依據，不生成沒有統計基礎的百分比或人格分數。
先把方向說明發給我，方便選擇；需要用圖說明時同時提供我可以查看的圖片或文件。
選定後，把最終頁面內容、結構、視覺和手機端安排保存為共用目錄中的 design.md。
```

```text
【畫像網站工程師任務】
讀取共用專案目錄中的 profile.md 和 design.md，按選定方案建立可以執行的個人畫像網站，文件放在專案目錄內。
保留推文依據和原文連結。打開頁面檢查桌面端與手機端，修復排版、內容和連結問題。
返回我能打開的預覽及實際截圖，先等待我檢查，再進行發表。
```

ローカルプレビューでファーストビューのテキスト、カードの餘白、モバイル表示を確認し、問題がなければエンジニアにパッケージングさせ、**Vercel または Cloudflare Pages にプッシュして公開します**。

**アプローチ2：パラメータによる組み合わせと動畫・音聲の切り抜き（鐵柱 / 公式ツールプラン）**
- キャラクターとコーディネート：ゲームデータの著せ替え（ペーパードール）システムを利用し、Bot がパラメータを分析した上でサードパーティ API を呼び出して合成。
- 動畫の切り抜き：公式の Clip Bot テンプレートを使用し、動畫・音聲の長尺 URL を直接入力することで、タイムスタンプ付き原稿を自動書き起こしし、要點クリップを切り出し。

**検収基準**
- ローカルプレビューのレイアウトが整っており、モバイル端末でのレスポンシブ表示が正常であること。
- 引用されたポストにすべて元リンクが付いており、正しく遷移できること。
- ページが本人の実際の表現に忠実であり、経歴を捏造していないこと。

### 配信、振り返り、レビュー：人間のチェックゲートと時間差ワークフロー

初心者は完全自動・無人運用を求めがちですが、これはアカウント凍結につながりやすいです。**クラウド PC の仮想マシン內のブラウザで投稿することは厳禁です**。プラットフォームのリスク検知システムは仮想マシンのフィンガープリントを識別できます。投稿には必ず絶対的な人間の介入ゲートを設け、発信者本人がローカルの実機デバイスから手動で投稿する必要があります。

チームの連攜には時間差アプローチを採用し、一日中畫面を見張る必要をなくします：
- 企畫プールは週単位で決定：毎週30分かけてスプレッドシートから候補カードを選び、承認のチェックを入れる。
- 初稿は日単位で確認：発信者が毎日10分かけて `04-review/` 內の原稿を確認し、個人的な所感を1段落書き加える。
- ステータスカンバンで進行管理：スプレッドシート上で「審査待ち」「執筆中」「確定済み」「公開済み」のステータスフローを回す。

### 事例 1：Adrian Punk の5人完結型個人メディアチーム

Adrian Punk（@AdrianPunk115）はデスクトップ版で5人の長期的な専任 Bot チームを構築し、一次情報の収集、企畫選定、執筆、校正から振り返りまでのクローズドループを確立しました。

1. **事前の権限引き締め**：クライアントの設定で「このコンピュータ上で実行」を「許可しない」に設定し、プロンプトで無斷投稿、パスワードの代理入力、コネクタの呼び出しを明文で禁止。
2. **ファイルパスの構築**：クラウド PC 上に `/workspace/content-team/` と7つのサブディレクトリを作成し、`00-profile/voice.md` にアカウントのトーン、代表作、禁止ワードを格納。

4. **規約に基づく引き継ぎ**：「個人メディア・コンテンツチーム」グループで開始コマンドを送信。上流のアウトプットを Markdown として書き出して下流が読み込めるようにし、**人間の承認なしにプロセスを勝手に進めることを禁止**。

注意：5體の Bot はクラウド PC を共有しておりサンドボックスによる隔離がないため、権限管理は明確な役割の境界線に依存する必要があります。**ファクトチェッカーは必ず獨立して元リンクと照合し**、メインライターが捏造した數値や PR 調の表現をフィルタリングしなければなりません。

鐵柱AGI（@cgnot996）は Bot の境界を體系的にテストし、凍結防止とディザスタリカバリのソリューションを體系化しました。

2. **超高速インプット**：モバイル端末側でショートカットを設定してクリップボードを読み取り、Webhook 経由でクラウド PC 內の Bot に直接送信してスプレッドシートに蓄積。
3. **凍結防止のレッドライン**：**仮想マシン內のブラウザで投稿をシミュレートすると極めて凍結されやすいため、外部への投稿ややり取りは必ず人間が実機デバイスで実行すること**。
4. **ディザスタリカバリ**：クラウド PC を再構築すると非永続環境がクリアされるため、Shell による自動復舊スクリプトを用意し、Memory Manager Bot を設定してプロンプトや設定を定期的にバックアップ。

注意：**主要な設定やインストールコマンドは必ずワンクリックで再現可能な復舊スクリプトとして整備すること**。クラウド PC を絶対的に安定したサーバーと見なしてはなりません。

## 陥りがちな落とし穴

1. クラウド PC からの投稿はフィンガープリントが露出して凍結されやすく、完全自動化は誤投稿の原因にもなります。**投稿、いいね、DM は必ず実機で手動で行ってください**。
2. ロール定義に**厳格なルールを設定する：「データなしは『未検出』と明記」「推論には『推測』と付記」**。虛偽データの混入を防ぎます。
3. クラウド PC のリセットにより依存関係がクリアされます。**Shell 復舊スクリプトを永続ディレクトリに保存**して備えてください。
4. Routine タスクの**実行週期を入念に確認する**。「平日のみ実行」と誤設定して週末に連攜が途切れるのを防ぎます。
5. 絵コンテ/シーンフィルタリングを行わなかったことで週間クレジットが40%以上激減した事例があります。**高頻度の無駄なポーリングを厳禁とし、トリガーのタイミングを最適化してください**。

## 完了後の検収手順

### 権限とディレクトリ
1. アカウント設定「一般（General） → Agent → このコンピュータ上で実行（Run on this computer）」を開き、**ステータスが「許可しない（Never）」になっていることを確認します**。Bot による自動投稿や決済は厳禁であり、データの捏造も認められません。
2. `/workspace/content-team/` 配下の7つのサブディレクトリを確認し、`00-profile/voice.md` にアカウントのポジショニング、サンプル、禁止ワードを記入します。

### 取材・執筆とリハーサル
1. 情報を3件収集し、**そのうち2件のリンクがアクセス可能かつ原文の裡付けがあることを抜き取りテストします**。データが不足している場合は「公開データが見つかりません」と明記し、數値やフォロワー數の憶測は禁止します。
2. Brief を確認した後に初稿を作成します。冒頭2文で直接核心となる事実を伝え、段落は2〜4文を維持し、原稿の末尾に事実の根拠と要確認事項を添付し、禁止ワードを完全に排除します。
3. 校正原稿では事実確認のみを行い新たな論點を追加せず、**人間の指示なしに自動で外部送信することは決してしません**。テスト環境で `restore.sh` を一度実行し、依存環境が正常に整っていることを確認します。

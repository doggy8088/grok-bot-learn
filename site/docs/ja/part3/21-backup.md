# 第 21 章 バックアップと復元：コンピュータがリセットされても慌てない

クラウドコンピュータがリセットされると環境は完全に初期化されます。記憶を頼りに `apt-get` や `pip install` を実行しても依存関係や環境変數を漏らしやすく、調整を重ねた Bot の記憶にもエクスポートボタンはありません。**解決策は、ディザスタリカバリを2系統の並行パイプラインに分割することです。**

1. **仮想マシンサービス**：登録台帳と自動復元スクリプトでシステム依存関係を管理する。
2. **エージェントの記憶**：専任の記憶マネージャーが設定と動的事実を Markdown に書き出し、プライベート Git リポジトリにプッシュする。

構築完了後は、**システムがリセットされたり移行したりしても、最小限の人的介入ですべてのサービスと記憶を復元できます**。


![バックアップと復元：コンピュータがリセットされても慌てない](/info/21-backup.png)

## 21.1 クラウドコンピュータの実態を把握する：更新、Recover、Reset の違いとは

![21.1 クラウドコンピュータの実態を把握する：更新、Recover、Reset の違いとは](/info/21-backup-s1.png)

**同一アカウント下のすべての Bot は同じ仮想マシンを共用**しており、`/workspace` ディレクトリとシステムプロセスを共有しています。1台のマシンにグローバルツールをインストールすれば他の Bot も呼び出せますが、マシンがリセットされるとすべての依存環境が同時に失われます。

參考：[『4.6 仮想マシン、記憶とバックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)。

クライアントの **Settings** > **電腦** にある **Bot's 電腦** の下でコントロール項目が提供されています。3者の違いは以下のとおりです：

| 操作 | 仕組み | 保持される內容 | 失われる內容 |
| :--- | :--- | :--- | :--- |
| **更新（Update）** | 環境イメージをアップグレード。ソフトウェア更新とコンピュータ更新の2種類がある | ソフトウェア更新はすべて保持。コンピュータ更新はボット、ファイル、ログイン情報を保持 | ソフトウェア更新での損失なし。コンピュータ更新ではグローバルアプリケーションとパッケージが削除される |
| **Recover** | 保存済みデータをもとに最新イメージで新しいマシンを作成し、まず古いマシンに接続してデータを保存しようとする | 保存済みのボット、ファイル、ログイン情報 | グローバルアプリケーションとパッケージ。古いマシンに接続できない場合、未同期の変更は失われる |
| **Reset** | 直近に保存されたデータをもとに直接新しいマシンを作成し、実行中のタスクを中斷する | 保存済みのボット、ファイル、ログイン情報 | グローバルアプリケーションとパッケージ。未同期の変更は失われる |

対話履歴はクラウドに保存されているため、マシンのリセットやファイルの誤削除による影響はありません。しかし、**グローバルにインストールされたアプリケーションパッケージ、`node_modules`、Python 仮想環境は公式には保存されず**、コンピュータ更新、Recover、または Reset の際にすべて消去されます。

詳細は [『Grok Bot コンピュータ』](https://cursor.com/cn/help/grok-bot/computer-recovery) を參照してください。

仮想マシンがフリーズしたり応答が例外になったりした場合は、次の順序でトラブルシューティングを行ってください：

1. **Reconnecting** または **Couldn't Reach Grok Bot's 電腦** と表示される：ネットワークの揺らぎによるものです。少し待ってから **Retry** をクリックしてください。再接続中にファイルが失われることはありません。**この段階で Reset をクリックすることは厳禁です**。
2. クライアントを再起動する。Mac ユーザーは必ずトップメニューバーから **Quit** を選択してください。単にウィンドウの赤い「×」ボタンをクリックしただけでは終了しません。
3. アップデートを確認する。**Settings** > **電腦** に進み、利用可能なアップデートがあれば先に **更新** をクリックします。エージェントが一時停止していない旨が表示された場合は、現在のタスクが終了するのを待ってからクリックします。
4. 復元を試みる。それでも接続できないか、更新が停止して **恢復電腦** と表示された場合は **Recover** をクリックします。**Update 仍在執行** と表示された場合は、**Keep waiting** を選択します。
5. **Reset** を実行する。ステップ1〜4が無効な場合のみ Reset をクリックします。失敗した場合は **Retry Recover** または **Retry Reset** で再試行し、エラーが続く場合は公式サポートにお問い合わせください。
6. ディスク容量のアラートに対処する。

   **Computer is low on disk space** または **Computer is critically low on disk space** という通知を受け取っても、手動でファイルを削除しないでください。サイドバーの **Go to Disk Saver** をクリックして解決策を確認します。確認なしにシステムがファイルを削除することはありません。

   詳細は [『Grok Bot コンピュータ』](https://cursor.com/cn/help/grok-bot/computer-recovery) を參照してください。

**クラウドコンピュータは使い捨てのコンテナにすぎません**。手動で環境を微調整しないでください。環境構築プロセスをすべてスクリプト化し、設定と自作ソースコードは必ず外部のプライベート Git リポジトリに保存してください。

## 21.2 仮想マシンサービス台帳と自動復元パイプライン

![21.2 仮想マシンサービス台帳と自動復元パイプライン](/info/21-backup-s2.png)

[『4.6 仮想マシン、記憶とバックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)

クラウドコンピュータでは低レイヤーのスナップショットが提供されないため、**再構築プロセスをワンクリックスクリプトにするのが最も低コストです**。

### サービス台帳と汚染防止バックアップ

プライベートリポジトリに `vm-services/` ディレクトリを作成し、人間が読むための `REGISTRY.md` テーブルと、自動化スクリプトが解析する `registry.json` を組態します。

台帳とバックアップには、遵守すべき厳格なルールがいくつかあります。
- 登録フィールドには、サービスID、擔當Bot、コードパス、インストール依存関係（apt/pip/Docker/cron）、起動・停止およびヘルスチェックコマンド、復元が必須かどうかを含めます。
- **認証情報のパスにはローカルの絶対パス（`~/.env` など）のみを記述し、平文での保存は厳禁です**。QRコード読み取りや OAuth などの手動手順は個別にハイライトします。
- 自作スクリプトは単獨で `service-src/` に保存し、`venv/`、`node_modules/`、ログを除外します。**コミット前には必ず正規表現で秘密鍵やシークレットのスキャンを実行してください**。

### 自動復元パイプライン

`vm-services/restore/` 內に各サービス専用のサブスクリプトを作成します。**スクリプトは必ず冪等性を擔保してください**。2回連続で実行してもディレクトリの重複やポートの競合エラーが発生しないようにします。

メインエントリである `restore-all.sh` は、依存関係の順序に従って順次直列実行します。
1. **基本依存関係**：`cron`、`ffmpeg`、`yt-dlp` などのシステムツールをインストールします。
2. **ソースコードの組態**：`service-src/` から自作スクリプトをコピーし、既存のファイルはスキップして不足分のみを補完します。
3. **環境とパッケージ**：Python 仮想環境を作成し、`pip install -r requirements.txt` を実行します。
4. **常駐プロセスの起動**：バックグラウンドの常駐プロセスを起動します。
5. **定期タスクの登録**：統一された crontab スケジュールを復元します。
6. **ヘルスチェック**：プロセスの稼働を1つずつ確認します。**失敗した場合はエラーログを記録して次の項目に進み**、処理を中斷・ブロックさせません。

[『Grok Bot 仮想マシンリセット後にツールが全部消えた？バックアップ・復元チュートリアル（プロンプト付き）』](https://jcng5q8n0f3z.feishu.cn/wiki/Q6ZdwzjO5i6z0pkdMfyca8Cbnye)

## 21.3 記憶マネージャー：Bot の中核記憶をプライベートリポジトリに格納する

![21.3 記憶マネージャー：Bot の中核記憶をプライベートリポジトリに格納する](/info/21-backup-s3.png)

公式には完全な記憶をエクスポートするボタンが用意されていないため、アカウント変更やシステム移行時に設定や好みが非常に失われやすいです。**専任の「記憶マネージャー」Bot を用意し、形のない記憶をプライベート Git リポジトリのプレーンテキストスナップショットに変換するのが最も安全です。**

[『Grok Bot 百萬撤退：完璧な Agent システムバックアップソリューション』](https://jcng5q8n0f3z.feishu.cn/wiki/W0TCwnTmbiIJ9KkF4S4cV6ifnCh)

### 記憶の階層化と保守原則

| 階層 | 含まれる內容 | 説明と権限 |
|---|---|---|
| **共有層** | アカウント共有記憶、共通 Skill、プラグイン設定 | すべての Bot が読み取り可能 |
| **専有層** | Description ルール規約、専有の獨立記憶、Routine タスク | 個々の Bot が排他的に保持 |

- 動的な事実はコンテキストに長期的に溜め込まず、アクセス方法のみを記録し、使用時にオリジンから再取得します。
- 共有記憶は、相互汚染を防ぐため、人間によるレビューまたは標準化されたワークフローによる検証を経る必要があります。
- **ビジネス定義は記憶に書き込み、固定された操作フローは必ず Skill コードとして定著させます。**

[『4.6 仮想マシン、記憶とバックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)

### アーカイブ仕様とワークフロー

::: details アーカイブ仕様とワークフロー
```text
├── bots/                     # 各 Bot 獨立組態與記憶
│   ├── cyber-xiaowan/        # 單個 Bot 資料夾
│   │   ├── agent-spec.md     # 身份設定、名稱、bot-id、slug、description
│   │   ├── MEMORY.md         # 核心記憶全量快照
│   │   ├── profile.md        # 角色資訊與權限邊界
│   │   └── archive/          # 歷史版本與過往記錄
│   └── ...                   # 其他 Bot 目錄
├── meta/                     # 全域Metadata與多 Bot 拓撲關係
├── shared-user-memory/       # 帳號級共享記憶
├── vm-services/              # 虛擬機器服務總帳與恢復指令碼（見 21.2 節）
├── README.md                 # 倉庫使用說明與最新狀態
├── RESTORE.md                # 跨環境恢復操作 SOP
└── registry.md               # 登記索引
```
:::

個々の Bot ディレクトリ配下の `MEMORY.md` には、「ID・権限」「意思決定の責務」「現場スナップショット」の3層が含まれます。

1. **リストの列挙**：永続化バックアップが必要なコア Bot を選定します。
2. **スケジューリングと指示の配信**：各 Bot が自身の設定と記憶を読み取り、要約した上で `/workspace` 內の対応する Markdown ファイルに書き込みます。
3. **取得・検証・リポジトリ登録**：**平文の Token が含まれていないことをスキャン・確認した上で一括コミットし**、日付タグ（例: `tag-2026-10-15`）を付與してリモートのプライベートリポジトリにプッシュします。

**Bot はフルスナップショットを擔當し、Git は増分追跡を擔當します**。Bot は毎回直接ファイルをフル上書き保存し、過去の変更履歴は Git エンジンに蓄積させるため、プロンプト內で差分を計算する必要はありません。

## 21.4 実踐事例：鐵柱AGI の百萬撤退とサービスマネージャー

### 記憶マネージャーによるバックアップ

鐵柱（@cgnot996）は 21 體の Bot を運用・保守しています。アカウント停止による記憶消失を防ぐため、彼は「記憶マネージャー」Bot を構築し、Gitee のプライベートリポジトリと連攜させてアーカイブを行いました。

1. **コアの選定**：21 體の Bot から、まずは 7 體のコアを選んでテスト運用しました。
2. **エクスポートと確認**：7 體の Bot に設定と記憶をエクスポートするよう通知します。**一部の Bot はエクスポート完了後に無言になるため、指示の中で「書き込み完了後に報告すること」を必須とし、同時にマネージャーが `/workspace` ディレクトリをスキャンして照合します**。
3. **登録とタグ付け**：初回の 73KB をリポジトリにアーカイブし、`tag 2026-09-10` タグを付與してシークレットスキャンを通過させました。
4. **個別プロファイル構造**：「サイバー小晩」のように、`MEMORY.md`（約 21KB）にアイデンティティとスナップショットを保存し、`agent-spec.md` に bot-id と説明を保存します。
5. **定時実行の有効化**：定期的な自動アーカイブを設定します。

新しいアカウントにインポートした際の記憶再現率は約 80% でした。**ローカルでバックアップされていないファイル、対話履歴、サードパーティのログイン狀態は復元できません**。

Hermes や OpenClaw に移行する際は、`MEMORY.md` を記憶ディレクトリに組態し、`agent-spec.md` の description をシステムプロンプトに変更するだけで動作します。

[『Grok Bot 百萬撤退：完璧な Agent システムバックアップソリューション』](https://jcng5q8n0f3z.feishu.cn/wiki/W0TCwnTmbiIJ9KkF4S4cV6ifnCh)

### 仮想マシンサービスマネージャー

クラウドコンピュータがクラッシュしてリセットされると、ツールがすべて失われます。著者は Gitee の `grok-bot-memory` リポジトリにある `vm-services` ディレクトリに再構築台帳を記録しています。

1. **台帳への登録**：2026-10-10 時點で、10 體の Bot の 20 項目（常駐 4 項目、オンデマンドツール 14 項目、秘密鍵関連 2 項目）を登録し、そのうち 18 項目を「復元必須」とマークしました。
2. **サービスの分類**：常駐サービスにはスクレイピングサービス、Muse API ラッパー、メールエンジン、送信トンネルが含まれます。オンデマンドツール（ffmpeg、Chrome など）はインストールコマンドのみを記録し、Metaso と TikHub は秘密鍵のパスのみを記録します。
3. **クリーンなソースコードバックアップ**：自作ソースコードは約 5.1MB で、秘密鍵、ログ、ステータス履歴を除外しています。
4. **直列的な復元**：マネージャーが `restore/` ディレクトリと `restore-all.sh` を保守します。**マネージャーは普段は勝手に実行せず、人間の指示を待って依存関係順に起動し、受け入れチェックリストを提出します**。

[『Grok Bot 仮想マシンリセット後にツールが全部消えた？バックアップ・復元チュートリアル（プロンプト付き）』](https://jcng5q8n0f3z.feishu.cn/wiki/Q6ZdwzjO5i6z0pkdMfyca8Cbnye)

## 21.5 認証情報のセキュリティと手動承認ゲート：畫面は渡してもパスワードは渡さない

**複數の Bot が仮想マシンのディスクとブラウザセッションを共有しているため、Bot を新設するだけでは機密データを隔離できません。** スクリプトやチャット內に一度平文で書き込んでしまうと、他の Bot や外部ログからも読み取られてしまいます。

[『4.6 仮想マシン、記憶とバックアップ』](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)

### 認証情報はパスのみを殘し平文は殘さない

- Token や秘密鍵は、Git の管理対象外である `~/.env` またはグローバルシークレットディレクトリに保存します。
- `REGISTRY.md`、`registry.json`、および記憶ファイル內では、**認証情報に関するものはディスクの絶対パスのみを記録します**。
- チャット欄へのパスワード送信は厳禁とし、プッシュ前には必ず正規表現によるマスキングスキャンを実行します。

### 畫面は渡してもパスワードは渡さない

1. Bot が 2FA、QRコードスキャン、またはデバイス認証のポップアップに遭遇した場合、直ちに一時停止して人間に引き継ぎを通知します。
2. ユーザーはクライアントでクラウドコンピュータを全畫面表示にし、自分でパスワードを入力するかQRコードをスキャンします。
3. 完了後に制御権を戻すと、**Bot はセッション Cookie を引き継いで処理を続行し、平文パスワードに觸れることはありません**。

### 高リスク操作には Ask-first を設定する

- 投稿、決済、データ削除、低レイヤー環境の変更などの不可逆な操作は、必ずポップアップを表示して人間の承認を待つ必要があります。v0.70.2 ではこの種の確認ロジックが最適化されました。
- **Bot の自律権限は読み取り、公開検索、`/workspace` 內部の読み書きのみに限定され**、ルールが衝突した場合は Ask-first が優先されます。

## 21.6 すぐに使える3つのプロンプトセット

以下に、実際の運用で検証済みの3つのプロンプトを提供します。コピーして対応する Bot に送信するだけで、デプロイして使用できます。

### プロンプト1：クラウドコンピュータに「仮想マシンサービスマネージャー」を設定する

「仮想マシンサービスマネージャー」Bot を作成し、**設定に貼り付けます**：

::: details プロンプト1：クラウドコンピュータに「仮想マシンサービスマネージャー」を設定する
```text
你是「虛擬機器服務管家」，只管一件事：記下這台虛擬機器上部署過的所有第三方服務，並在電腦更新或換帳號之後，按記錄把它們原樣恢復。

你維護的東西
1. 一份登記總帳，人和機器各讀一份：REGISTRY.md（表格）和 registry.json（給指令碼讀）。
2. 每個服務一個恢復指令碼 restore/restore-<服務>.sh，必須冪等，重複跑也不會出錯。
3. 一個總入口 restore/restore-all.sh，按依賴順序呼叫各個恢復指令碼，最後彙總哪些失敗了。
4. 一份原始碼備份 service-src/：各 Bot 自己寫的服務程式碼和指令碼，同步時排除密鑰、記錄、執行狀態、虛擬環境和個人資料，並先掃一遍明文密鑰，命中就停。
5. 以上全部跟著一個私有 Git 倉庫存（「你的備份倉庫地址」）。總帳、恢復指令碼、原始碼都在倉庫裡，密鑰永遠不進倉庫。

登記規則（其他 Bot 部署任何服務都必須來找你登記）
每項必須包含：
- 名稱和短 id、用途、負責的 Bot
- 路徑：程式碼、組態、資料分別在哪
- 安裝方式和依賴（apt / pip / npm / Docker / 系統定時任務）
- 啟停命令、健康檢查命令
- 更新後的恢復步驟，或者對應的恢復指令碼
- 是否必恢復：是 / 否
- 密鑰：只寫存放路徑，絕不寫明文
- 需要真人完成的步驟（OAuth 登錄、掃碼、匯入 cookie）單獨標出來

你的工作方式
- 先弄清哪些會丟、哪些能留：電腦更新一般保留工作目錄，但系統包、常駐行程、全域安裝的命令列工具會丟；重置則什麼都不留。所以要記的是“怎麼重建”，不是去拷整台機器。
- 能從公開渠道重裝的（apt、pip、npm、上游 Git 倉庫）只記安裝命令；自己寫的程式碼必須進原始碼備份，否則重置後就找不回來。
- 收到登記先核對：路徑是否真實存在、健康檢查能不能過。登記寫的和實際不一樣時，以實際為準，並告訴負責的 Bot。
- 多個定時任務合併成一份 crontab 真源時，檢查每一條是不是都在真源裡，不在的要靠恢復指令碼補回去。
- 故意停掉的服務要寫清楚“為什麼停、什麼條件下重開”，免得被當成漏裝。
- 只有主人說“電腦更新完了”才跑總恢復，不盲跑。跑完交驗收：每項是成功、失敗，還是要真人處理。
- 每次有服務新增、刪除或原始碼大改，先重新同步原始碼備份，再把總帳、指令碼、原始碼一起提交推送到備份倉庫。換帳號或重置時，就靠這份備份把整套設定帶走。
- 刪掉的服務要徹底清除：總帳只反映現在真實的狀態。
```
:::

### プロンプト2：コンピュータのリセット後に Bot に全面復元を実行させる

**Git アクセストークン** を設定し、括弧內の內容を置き換えて Bot に送信します。

::: details プロンプト2：コンピュータのリセット後に Bot に全面復元を実行させる
```text
這台電腦剛重置過（或者是換了新帳號），之前部署的服務都沒了。請按我的備份把它們恢復到可用狀態，規則如下。

備份在哪
- 備份倉庫：<你的備份倉庫地址>，分支 <分支名>
- 倉庫裡有：登記總帳（REGISTRY.md 和 registry.json）、每個服務的恢復指令碼（restore/）、自寫服務的原始碼備份（service-src/）
- 倉庫裡沒有密鑰，這是故意的

請按這個順序做
1. 把備份倉庫拉到工作目錄，先讀總帳，告訴我一共登記了幾項、哪些標了「必恢復」、哪些只留密鑰不用恢復。先列出來，不要動手。
2. 把自寫服務的原始碼從 service-src/ 放回總帳寫的原位置。只補缺失的，已經存在的目錄不要覆蓋。
3. 按總帳的依賴順序逐項恢復：先裝系統依賴（比如 cron、ffmpeg），再裝命令列工具，最後拉起常駐服務和定時任務。每項都用它自己的恢復指令碼，指令碼要能重複跑。
4. 每裝完一項就跑它登記的健康檢查。失敗了先看記錄、試著修一次；修不好就記下原因，接著做下一項，不要卡住。
5. 把需要我本人做的事彙總成一張清單：要重新提供的密鑰（只說放哪個路徑、叫什麼名字，別讓我把密鑰貼進聊天）、要重新登錄授權的工具（OAuth、掃碼、設備碼）。然後一項一項帶我做，每做完一項馬上覆查。
6. 故意暫停的任務保持暫停，總帳裡寫了原因和重開條件的照辦。別因為“看起來漏裝了”就自作主張打開。
7. 最後交驗收清單，每項一行：服務名、結果（成功 / 失敗 / 等我處理）、健康檢查輸出摘要、花了多久。再告訴我總共用了多少時間、成功了幾項。

不要做的事
- 不要把任何密鑰寫進倉庫、記錄或聊天
- 不要跑總帳沒登記的安裝
- 不要用“重置電腦”當修復手段
- 恢復完如果有任何改動（路徑變了、版本升級了），更新總帳，提交推回備份倉庫
```
:::

### プロンプト3：記憶マネージャーの定期アーカイブ指示

**Routine または手動アーカイブ時にこちらを送信します：**

::: details プロンプト3：記憶マネージャーの定期アーカイブ指示
```text
請開始執行本週的智慧體記憶與設定歸檔任務。

執行步驟：
1. 枚舉當前工作區內所有處於活躍狀態的 Bot 名單，核對 bots/ 目錄下的已有目錄。
2. 逐個通知名單內的 Bot：讀取各自的 Description、人設規則與當前核心記憶，按三層結構（身份profile、歷史決策與職責、當前現場快照）提煉並覆蓋寫入 /workspace/bots/<bot-slug>/MEMORY.md。同時將身份Metadata更新至 agent-spec.md。
3. 檢查各 Bot 回執，並在 /workspace 目錄核對文件生成情況，確保所有目標 Bot 的 Markdown 均已寫出。
4. 提取帳號級共享記憶，更新至 shared-user-memory/ 目錄下的 Markdown 文件中。
5. 對本次生成的所有 Markdown 文件進行敏感資訊正則掃描，檢查是否存在明文 API Token、密碼或私鑰。如果發現疑似憑證，立即中斷並報警。
6. 掃描無例外後，執行 Git 操作：將所有更新文件暫存，提交資訊標記為「memory snapshot YYYY-MM-DD」，推送到遠端私有 Git 倉庫，並打上對應日期的 Git Tag。
7. 完成後向我彙報：本次歸檔了哪幾個 Bot、總文件大小、是否有失敗或超時的 Bot。
```
:::

## 21.7 よくある落とし穴

1. Reconnecting と表示された際は**Reset をクリックしないでください**。単なるネットワークの揺らぎやメンテナンスであり、クリックすると古いスナップショットで未保存データが上書きされてしまいます。
2. 複數デバイスで Codex の認証を共有すると互いにログアウトさせられるため、獨立したサブアカウントまたは固定された認証情報を割り當てる必要があります。
3. 定期タスクは統一して crontab 設定ファイルにまとめ、Git で管理して、マシンのリセットによる漏れを防ぎます。
4. サービス台帳は実際の運用コマンドを基準とし、環境に Docker がインストールされていないと復元スクリプトが停止する原因になります。
5. Bot のエクスポートは無言になりがちなため、マネージャーが積極的にディスクを確認し、指示で「書き込み完了後は必ず報告すること」を強く義務付けます。
6. **バックアップリポジトリは必ずプライベートに設定し、正規表現スキャンを追加してください**。Token が Git push によってパブリックリポジトリに流出するのを防ぎます。

## 21.8 完了後の受け入れテスト方法

### サービスとスクリプト
1. 台帳確認：`vm-services/REGISTRY.md` と照合し、`ps aux` でプロセスを、`netstat` または `ss` でポートを確認します。**パスの過剰記録や漏れがあってはなりません**。
2. テスト実行：個別に `restore-<服務名>.sh` を実行し、エラーなく繰り返し実行できるか確認します。
3. 全體リハーサル：一時ディレクトリにクローンした後、`bash restore/restore-all.sh` を実行し、**「復元必須」の項目がすべて成功することを確認します**。手動対応が必要な手順がリストアップされていることも確認します。

### リポジトリと記憶
1. 構造確認：Web畫面で `bots/` を確認し、各 Bot に獨立した `agent-spec.md` と `MEMORY.md` が存在することを確認します。
2. サンプリング検査：`MEMORY.md` を開き、「ID profile」「意思決定の履歴と責務」「現在の現場スナップショット」の3層が完全であり、空のテンプレートや文字化けがないことを確認します。
3. シークレット検索：全體を `sk-`、`Bearer`、`password` で検索し、**認証情報はローカルの絶対パスのみを殘し、平文 Token は厳禁です**。

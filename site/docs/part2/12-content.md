# 第 12 章 案例：自媒體與內容團隊

對話式 AI 容易丟上下文，**Grok Bot 用雲端電腦共享文件跑流水線**。

1. 編寫角色描述，按六組硬欄位建選題庫。
2. 調研 Bot 把卡片寫入目錄，主筆 Bot 讀取後起草文案。
3. 落地去 AI 腔審校規則，將推文轉成個人網站。
4. **關鍵發表節點必須人工把關**，規避虛假資料與平台風控。

## 自媒體團隊的崗位設計與協作機制

![自媒體團隊的崗位設計與協作機制](/info/12-content-s1.png)

### 是什麼

**在 Grok Bot 搭團隊，核心是「單崗單責」。** 帳號下所有 Bot 共享同一台雲端電腦（擁有獨立內核、記憶體和 `/workspace` 路徑），但各自擁有獨立的窗口、記憶與設定。

Bot 之間靠在共享資料夾讀寫 Markdown 文件交接任務。

### 怎麼做

**主 Bot 頭像帶星標（右鍵頭像可切換）**負責統籌派工，5 到 6 個專職 Bot 嚴格按職責邊界工作。

| 崗位名稱 | 交付路徑 | 核心職責與禁止操作 |
| :--- | :--- | :--- |
| 情報偵察員 | `/workspace/content-team/01-inbox/` | 蒐集一手線索。嚴禁互動發文與私信，嚴禁把二手言論當事實 |
| 選題策劃師 | `/workspace/content-team/02-briefs/` | 評估線索出 Brief。嚴禁外部衝浪，未獲人工批准不得推進到主筆 |
| 內容主筆 | `/workspace/content-team/03-drafts/` | 依 `voice.md` 寫作。嚴禁捏造事實與通用公關腔 |
| 事實編輯 | `/workspace/content-team/04-review/` | 核驗一手信源。無發表權限，證據衝突列出待確認 |
| 資料覆盤師 | `/workspace/content-team/06-analysis/` | 分析內容資料。嚴禁帳號互動，嚴禁將相關性寫成因果，缺資料嚴禁硬猜 |
| 網站工程師 | `/workspace/tweet-portrait/` | 提煉畫像建站。嚴禁偽造經歷，嚴禁把本地路徑當公網連結 |

1. 在雲端電腦終端建立標準共享目錄。
::: details 怎麼做
```text
/workspace/content-team/
├── 00-profile/     # 帳號定位、目標讀者、範文、禁用表達（voice.md）
├── 01-inbox/       # 情報偵察員的一手資訊卡
├── 02-briefs/      # 選題策劃師的選題 Brief
├── 03-drafts/      # 內容主筆的候選稿
├── 04-review/      # 事實編輯的審校稿
├── 05-published/   # 已發表文案存檔、資料截圖或 CSV
└── 06-analysis/    # 資料覆盤師的週報與實驗記錄
```
:::
2. 在 `00-profile/voice.md` 寫入風格基座，避免主筆產出套話。
::: details 怎麼做
```text
# 帳號定位
- 我長期寫：面向個人創業者與開發者的 AI 工具實測與提效工作流
- 我的目標讀者：正在用 AI 嘗試做獨立產品、做內容或做業務轉型的實幹者
- 讀者看完後應該獲得：直接能照著執行的步驟、準確的參數組態、明確的避坑提醒

# 寫作樣本
- 代表作 1：【粘貼一段自己資料最好、語言最順的代表作】
- 代表作 2：【粘貼一段帶步驟拆解的課程代表作】

# 表達習慣
- 常用語氣：像跟坐在對面的朋友覆盤經驗，冷靜、直白、短句為主
- 禁用表達：我的判斷是、毫無疑問、重塑格局、顛覆行業、進入新時代、不難看出
- 不會公開談論的內容：未經實測的空頭八卦、無法復現的玄學跑分

# 商業與事實邊界
- 必須保留原始來源的主張：所有關於產品上線、價格變動、官方改版的陳述
- 未親測時的寫法：必須明確標明“未核實”或“作者自述”
```
:::
3. **建群分發規則**。點選「新建聊天」建立「自媒體內容團隊」群聊並拉入全員。初次切忌直接指派選題，必須先發統一規範。
```text
這是“自媒體內容團隊”協作群。工作順序固定為：情報偵察員 → 選題策劃師 → 內容主筆 → 事實編輯；內容發表後，資料覆盤師讀取授權資料 → 06-analysis。所有中間文件放到 /workspace/content-team/ 對應目錄。任何登錄、外發、發表、按讚、回覆、關注、私信、購買、刪除、連線器授權或權限修改都必須先獲得使用者明確批准。本次僅確認收到和各自交付路徑，不執行外部操作。
```

### 選題與情報：抓取、指標與動機拆解

> 來源：[做自媒體怎麼用好 Grok bot](https://x.com/KinGao476942/status/2099736121781764594)  
> 作者：[Kin @KinGao476942](https://x.com/KinGao476942)

找選題別直接跟通用模型閒聊，它只會吐過時新聞。這裡讓偵察 Bot 模擬檢索或盯盤，把線索整理成卡片。

先給偵察員配好長期崗位提示詞：

::: details 選題與情報：抓取、指標與動機拆解
```text
你是我的情報偵察員（Scout）。唯一職責是發現、核驗並沉澱可用於選題的公開資訊，為後續選題提供證據；不寫成稿，不替使用者下結論。

【允許使用】
- 公共互聯網中的官方公告、產品文件、論文、GitHub Release、作者原文與使用者提供材料。
- 知乎、微博、X、小紅書等平台的公開頁面、公開帖子和公開評論區，可用於搜尋線索、觀察討論和摘錄公開資訊。
- 共享目錄 /workspace/content-team/00-profile/ 與 /workspace/content-team/01-inbox/。
- 如頁面要求登錄、密碼、驗證碼、2FA、passkey，或需要擴大權限，必須立即停下並請求使用者接管。

【禁止】
- 不得發文、改帖、刪帖、按讚、轉發、收藏、關注、取關、評論、回覆或私信。
- 不得讀取私信、好友可見內容、非公開頁面或與任務無關的個人資料。
- 不得把平台使用者發言、熱榜或搜尋摘要直接當成已確認事實；它們只能標為“平台線索”或“觀點”，關鍵主張必須回到官方原文、一手材料或當事人公開內容核驗。
- 不得憑記憶補數位、日期、引語或因果。
- 不得索取或記錄帳號密碼與驗證碼。
- 不得執行本機命令，不得訪問本機文件。

【固定交付】
寫入 /workspace/content-team/01-inbox/YYYY-MM-DD.md，每次最多 8 條。每條包含：事實或平台線索、來源平台、原始連結、證據摘錄、討論熱度或代表性觀點、為什麼值得關注、一個待核查問題、核驗狀態。
```
:::

**選題庫必須卡死六組硬欄位**，少一組直接作廢：
- 來源與新鮮度：原帖可打開的永久連結、發表時間與距今時長，不寫“某博主”。
- 可見資料：閱讀播放量、按讚量、轉發量和評論數共 4 項及抓取時間。找不到標“未找到公開資料”，嚴禁估算。
- 作者分層：記錄 handle、粉絲量與分層。低粉高爆學結構，頭部大 V 看議題。
- 社群分層：明確歸類為官方、國內或海外。
- 適合理由與執行角度：綁定自身優勢，寫明具體動作（如做實測、補步驟或給樣板），不寫空泛的“很火”。
- 動機拆解：涵蓋要害、爽點與互動動機。缺乏資料支撐的推論末尾必須標「推斷」。

策劃師從 `01-inbox/` 挑出 3 個高價值選題，按事實具體、讀者相關、作者有話可說這三道門篩出 Brief，寫入 `02-briefs/`：

```text
讀取今天 01-inbox 中已經核驗的線索，按照帳號定位篩選 3 個候選題，寫入 02-briefs/YYYY-MM-DD.md。每題包含：一句話事實、讀者場景、單一主角度、原始連結與證據、資訊缺口、建議內容形式、給主筆的寫作任務。證據不足的題直接標“待補證”。完成後停下，等待我批准，不要通知內容主筆。
```

如果搭建思路卡住，用訪談詞讓主 Bot 提問幫你理清需求：

::: details 選題與情報：抓取、指標與動機拆解
```text
我想新建一個 Bot，幫我做一件需要重複做的工作。請你先通過提問把這件事瞭解清楚，再幫我把這個 Bot 建立出來。

提問的時候：
- 一次只問一個問題，用大白話問，我回答完再問下一個。
- 我回答得不清楚的地方，你可以追問，也可以給我幾個選項讓我選擇。
- 你需要了解清楚這幾件事：這個 Bot 主要負責什麼，做完以後要交給我什麼，要去哪裡做、用哪個帳號，每一步要怎麼做、做到什麼程度算完成，遇到什麼情況要先停下來問我，結果放在哪裡，什麼時候執行。
- 有些問題我也不知道答案，你就先去搜尋解決方案，把你建議的做法告訴我，我確認以後再繼續。

問完以後：
- 先把你瞭解到的內容整理成一份崗位說明給我看，我確認沒問題以後，再建立這個 Bot，並且設定好例行任務。
- 建立好以後，先試著執行一遍，把結果拿給我看。
- 登錄、付款、發表、刪除這些操作，都要先問過我。
```
:::

**驗收標準**
- 原始連結全能打開，核心事實有原文支撐。
- 缺證據歸入“待補證”，**沒有人工簽字確認絕不流入主筆環節**。

### 起草與文案：去除 AI 腔與結構化輸出

寫初稿要先把主語從“產品有什麼”切成“對讀者有什麼用”，**讓讀者在前三秒看到明確資訊增量**。

文案可直接套用兩套經過驗證的框架：
- 影視颶風 Tim 的 HKRR 公式：涵蓋快樂、知識、共鳴與節奏。單篇至少佔穩一項，佔兩項算優秀，一項不佔直接廢棄。
- 潘亂的轉發動機：圍繞“跟我有關”，主語換成讀者。比如別寫“軟體更新了”，寫成“你每天找選題省下了兩小時”。爆款結構可以複用，抄節奏不抄內容。

主筆填入明確寫作規則與禁令：

::: details 起草與文案：去除 AI 腔與結構化輸出
```text
你是我的內容主筆（Writer）。唯一職責是把已經批准的 brief 寫成候選稿；不負責找熱點、補事實、決定選題或發表。

【允許使用】
- /workspace/content-team/00-profile/voice.md 中的定位、範文、禁用句式與術語。
- /workspace/content-team/02-briefs/ 中已經批准的事實、連結、角度和限制。
- 輸出到 /workspace/content-team/03-drafts/。

【禁止】
- 不得自行瀏覽外部網站、登錄平台或呼叫連線器。
- 不得自行補充數位、引語、案例、比較級或因果。
- 不得偽裝親測、內幕或使用者回饋。
- 不得發送、發表、購買、刪除或修改權限。
- 不得執行本機命令，不得訪問本機文件。

【寫作規則】
前兩句說清發生了什麼，再寫具體後果、使用場景、矛盾或尚未解決的問題。觀點必須從 brief 中的事實長出來。段落以 2–4 句為主，句子長短交替，保留自然停頓。

【禁用表達】
“我的判斷是”“真正有價值的是”“這說明”“這意味著”“毫無疑問”“重塑格局”“進入新時代”，以及空泛三段式、硬湊金句、廣告腔和故作深刻的反問。

【固定交付】
按任務需要輸出：A. 140–220 字中文短帖；B. 280–420 字展開版；C. 僅在適合時給 3–5 條串文大綱；D. 使用者明確要求時寫長文。每份稿末附“事實依據”和“仍需確認”。完成後寫入 /workspace/content-team/03-drafts/YYYY-MM-DD-題目.md，並只彙報文件路徑。
```
:::

初稿完成後由事實編輯把關。**事實編輯只核實主張並修掉 AI 腔**，不擴充新觀點，也沒有發表權限：

::: details 起草與文案：去除 AI 腔與結構化輸出
```text
你是我的事實編輯（Editor），負責發表前的事實核驗、結構檢查和風格審校。你只做讓內容可信、清楚、像真人表達所必需的修改；你沒有發表權限。

【允許使用】
- /workspace/content-team/00-profile/voice.md、/02-briefs/ 與 /03-drafts/。
- brief 中列出的原始公開連結，僅用於複核關鍵事實。
- 輸出到 /workspace/content-team/04-review/。

【審稿原則】
1. 沒看過原始材料的人也能讀懂。
2. 一手來源足以支撐關鍵事實。
3. 事實、觀點和假設明確分開。
4. 刪除樣板腔、廣告腔、絕對化和生硬縮略語。
5. 不讓讀者誤以為作者親測、掌握內幕或獲得使用者回饋。
6. 無法核對的句子必須刪除、改成疑問或標記“待確認”。

【固定交付】
寫入 /workspace/content-team/04-review/YYYY-MM-DD-題目.md，包含：可發表候選版本、改動說明、風險標記、仍需人工確認、原始來源清單。完成後只彙報文件路徑和是否達到“可發表候選”標準。
```
:::

**驗收標準**
- 正文前兩句直接切入核心事實，不寫空話。
- 事實編輯逐條對照一手鍊接，無法驗證的標“待確認”或直接刪掉。
- 審校稿移入 `04-review/` 目錄等待人工終審。

### 配圖與視覺呈現：程式碼化建站與素材拼裝

> 來源：[把自己的推文做成個人畫像網站,  用 Grok Bot 從分析特點到上線分享保姆級課程](https://x.com/0xlangeai/status/2109115005069341175)  
> 作者：[藍哥AI @0xlangeai](https://x.com/0xlangeai)

![把自己的推文做成個人畫像網站,  用 Grok Bot 從分析特點到上線分享保姆級課程](/cases-img/fs32-0.jpg)

![把自己的推文做成個人畫像網站,  用 Grok Bot 從分析特點到上線分享保姆級課程](/cases-img/fs32-1.jpg)

自媒體配圖別讓 AI 隨手畫概念圖，滿屏塑料感。實操通常走兩條實在路徑：

**路徑一：把推文做成個人畫像網站（藍哥AI 方案）**
在「推文畫像網站」群裡由 4 個 Bot 接力，中間文件沉澱在 `/workspace/tweet-portrait/`：
1. 推文整理員抓取歷史推文，畫像分析師提煉表達習慣與反差。
2. 網站設計師出視覺佈局方案，網站工程師寫前端程式碼並做手機端適配。

前兩個角色按順序執行提示詞：

```text
【推文整理員任務】
確認我自己已綁定的 X 帳號身份，讀取最近 90 天內最多 100 條本人內容，包括原創、帶有本人評論的引用推文和本人回覆，排除純轉發。
建立一個名為 tweet-portrait 的共用專案目錄，將素材保存為 tweets.md。每條保留正文、日期、連結和內容型別，並註明實際讀取範圍、數量與缺失情況。
```

### 分發、覆盤與審核：人閘把關與錯位流轉

新手常追求全自動無人值守，這很容易導致封號。**嚴禁在雲端電腦虛擬機器內用瀏覽器發文**，平台風控能識別虛擬機器指紋。發文必須設絕對人閘，由博主本人在本地真實設備上手動發表。

團隊協作採用時間錯位法，不必整天守著螢幕：
- 選題池按周定：每週花 30 分鐘在表格裡挑候選卡片，勾選通過。
- 初稿按日看：博主每天花 10 分鐘看 `04-review/` 裡的稿件，補上一段個人體會。
- 狀態看板流轉：在表格裡跑通待審、寫作中、已定稿和已發表狀態。

## 容易踩的坑

1. 雲端電腦發文會暴露指紋被封，全自動也易亂髮。**發文、按讚與私信必須在真機手動發**。
2. 角色描述**寫死規則：無資料標“未找到”，推論打「推斷」**，防假資料入庫。
3. 雲端電腦重置會清空依賴。**把 Shell 恢復指令碼存入持久化目錄**備用。
4. Routine 任務**仔細核對執行週期**，防誤設“僅工作日執行”導致週末斷連。
5. 沒做分鏡過濾曾致單週額度驟減 40%+，**嚴禁高頻空轉輪詢，優化觸發時機**。

## 做完怎麼驗收

### 權限與目錄
1. 進帳戶設定「常規 → Agent → 在這台電腦上執行」，**狀態必須是「從不允許」**。Bot 嚴禁自動發文和支付，不準編造資料。
2. 檢查 `/workspace/content-team/` 下 7 個子目錄，並在 `00-profile/voice.md` 填好帳號定位、範本與禁用詞。

### 採寫與演練
1. 抓 3 條線索，**抽測 2 條連結可訪問且有原文支撐**；缺資料標明“未找到公開資料”，不準臆測數位或粉絲量。
2. 確認 Brief 後出初稿，前兩句直接給核心事實，段落保持 2 到 4 句，稿末附事實依據與待確認項，完全規避禁用詞。
3. 審校稿僅核實不加新論點，**沒人工指令絕不自動外發**。測試環境跑一次 `restore.sh`，核對依賴環境正常就緒。

## 1+N 主 Bot 派活模式：單入口與履約章程

別讓所有 Bot 都對接使用者，免得你在窗口間傳話，群聊也白耗 Token。**推薦採用 1+N 模式，你只跟統籌主 Bot 溝通**，由它拆解、派活與彙總，詳見 [《從一個 Bot 到一整個組織，Grok Bot 的進階用法分享：本地電腦、AI 分工和知識庫怎麼接起來》](https://jcng5q8n0f3z.feishu.cn/wiki/DdqFwLmn7i8cV1kYtDwc840enLg)。

### 主 Bot 六行章程與專職邊界

**主 Bot 只負責路由與監督，絕不能親自寫長程式碼或長文。** 在 Profile Description 寫入六行章程，使其無事靜默、有事派活，超長彙報存為文件。團隊組織規範參考 [《4.2 團隊編排：章程、崗位與放權》](https://jcng5q8n0f3z.feishu.cn/wiki/POTrwwThoiQxIakFDIDcUcKjnmh)。

```text
Own: 負責需求的統一拆解、分派、彙總與五行簡報彙報。
Sources: 人工下發的指令、項目看板文件。
Output: 純文字狀態摘要，超出五行時輸出為指定文件路徑。
Approval: 任何對外通信、採購、刪除操作必須暫停等待確認。
Failure: 下游專職 Bot 報錯時如實上報，不使用過期資料假裝完成。
Never: 永遠不直接編寫業務程式碼，不擅自修改生產組態。
```

專職 Bot 須在 Description 寫死負向邊界：
- 廣告投手 Bot：分析資料並出具待批清單，**絕不碰後台與出價，不調預算，也不加詞或建組**。
- 文案創作 Bot：只出草稿文件，嚴禁調介面直接上線公開內容。
- 競品調研 Bot：前台只看不動，嚴禁下單加購，也不留評或向賣家提問，防反爬封禁。

投放專員直接套用提示詞樣板。

```text
Own: 負責廣告投放資料診斷與策略輸出。
Sources: 運營分析文件 /workspace/project/ad_data.json。
Output: 待批操作清單 /workspace/project/pending_actions.md，列出出價建議與預期影響。
Approval: 絕不直接寫入廣告後台，不修改出價，不修改預算，不加否定詞，所有操作必須等待人工審批。
Failure: 資料缺失時明確標註缺失欄位，不推測填充。
Never: 絕不執行任何後台寫入與線上提交操作。
```

### 待批清單與驗收

**專職 Bot 只輸出結構化待批清單，把決定權留給人工。** 比如主 Bot 彙總出 5 條廣告出價衝突項，你回覆“確認建議”或批註修改後才觸發下一步。

系統達標後按三項標準驗收：

| 驗收項 | 達標標準 |
| --- | --- |
| 交互與主 Bot | 單入口清晰執行；主 Bot 不寫長程式碼、不寫長文章 |
| 專職 Bot | 各司其職，只產出結構化清單 |
| 高風險動作 | 不可逆操作均有明確人工確認卡點 |
